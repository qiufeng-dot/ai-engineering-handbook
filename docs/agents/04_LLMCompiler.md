## 研究起点：模型会调用工具，还不等于会合理安排等待

要比较 Scott Derrickson 和 Ed Wood 是否具有相同国籍，可以先查前者，再查后者，最后比较。也可以同时发出两个查询，等两边结果都回来后再比较。两种做法所需的信息相同，但后一种不必把两段搜索等待首尾相接。这就是论文图 1 选择这个问题的原因：依赖关系很简单，顺序执行造成的等待也很直观。[图 1，PDF 第 2 页](https://arxiv.org/pdf/2312.04511v3#page=2)

ReAct 每收到一次观察，再决定下一步，适合需要随环境变化的任务。代价是两个本可独立执行的查询，通常仍经历两轮模型生成和两段工具等待。ReWOO 已经说明，未来结果的具体值可以暂时未知，只要它将被用到哪里是可预见的，就能先写出带变量引用的计划。LLMCompiler 进一步追问：既然调用及其输入依赖已经写出来，能否让普通程序负责判断哪些可以启动，而不让模型逐次发号施令？

“Compiler”借用了编译器的组织方式：先把较高层的任务描述转换成可执行结构，再安排执行。这里没有证明自然语言任务经过转换后一定语义等价，也没有训练一种新模型。研究对象是模型外围的调用系统：怎样减少重复规划、重叠独立工具的等待，并在新信息到来后生成下一轮计划。

论文讨论的近邻包括按观察逐步行动的 ReAct、将规划与观察分开的 ReWOO，以及让独立回答片段并行生成的 Skeleton-of-Thought。它还与当时 OpenAI 的并行函数调用比较。后一项是 2023 年指定版本服务的实验，不能把其优劣直接当作今天产品能力的结论。[相关工作、§3，PDF 第 3–5 页](https://arxiv.org/pdf/2312.04511v3#page=3)

## 从“先后顺序”走向“谁需要谁的结果”

假设问题变成：斯坦福大学和 UCLA 的诺贝尔奖获得者数量之和，与伯克利的数量相比哪边更多？图 3 的安排是先查三所学校，前两项结果相加，再与第三项比较。三次搜索之间没有输入依赖；求和必须等前两次搜索；最终比较必须等求和与伯克利的搜索。[图 3，PDF 第 6 页](https://arxiv.org/pdf/2312.04511v3#page=6)

把每项调用画成一个点，把“这个结果是下一项的输入”画成箭头，就得到一张有方向且没有循环依赖的图，即有向无环图，简称 DAG。它表达的不是一串固定步骤，而是若干必须遵守的先后关系。没有箭头连接的两项，才可能在输入齐备时同时执行。即使允许无限并行，求和也不能早于参与求和的数据返回。

论文把实现分成三个部分。首先是 Function Calling Planner，即调用规划器。模型根据问题、工具说明和示范，输出带唯一递增编号的调用项，用 `$1` 之类的引用表示早先调用的结果。其次是 Task Fetching Unit，即检查哪些任务已经可以启动的调度程序。它查看依赖，替换已经得到的结果，优先交出所有输入齐备的任务。最后是 Executor，即执行器，异步发出具体工具调用，并把结果交回来。[图 2、§3.1，PDF 第 4 页](https://arxiv.org/pdf/2312.04511v3#page=4)

第二个部分并不需要另一个语言模型。判断“第 3 项需要第 1 项和第 2 项，现在两个结果是否都存在”，是程序可以明确完成的工作。这种分工很关键：模型负责提出关系，程序负责遵守关系。程序能够保证按某张图执行，却不能仅凭编号正确就保证这张图忠实表达了问题。

执行器还让不同调用使用各自的上下文，避免每个工具处理都带上全部历史。工具也可能包含语言模型。例如论文的数学工具会把自然语言计算请求翻译成数值表达式，再交给 `numexpr` 求值。因此“使用计算工具”并不消除前端选错属性、单位换算错误或表达式错误；只是把表达式已经正确之后的计算交给程序。[§4.1，PDF 第 7 页](https://arxiv.org/pdf/2312.04511v3#page=7)

图 2 的市值例子尤其适合练习检查语义。它问微软市值增长多少才能超过苹果，图中先查两家公司，再出现两项市值相除。**以下是读者检查，不是作者新增实验**：若微软当前市值为 M、苹果为 A，而且 A 大于 M，追平所需增长率是 A/M−1，严格超过还需大于这个值。单独的 M/A 不是增长率；后续语言模型仍可能从该比例转换出正确答案。因此这幅简图提醒我们区分“依赖安排正确”和“数学含义完整”，但不能仅凭它断定完整系统每次都算错。

## 两项扩展：计划还没写完就开始，结果回来后再计划

第一项扩展是流式执行。普通做法等完整计划生成后才启动工具，流式做法则在某条调用输出完整、依赖也已满足时立刻执行。模型继续生成后续任务，工具同时工作。它利用的是规划生成与工具等待之间的重叠，不会让有依赖的后继提前使用不存在的结果。[§3.2，PDF 第 5 页](https://arxiv.org/pdf/2312.04511v3#page=5)

第二项扩展是动态重规划。若新的观察决定下一轮究竟要做什么，系统先执行当前已知的图，再把结果交回规划器，生成下一张图。它不要求一次猜出未来所有分支。附录提示还用特殊结束调用来结束一轮计划，再由系统判断回答或继续规划；正文与不同提示里的 `finish`、`join` 命名不完全一致，本章解释其控制含义，不把提示文字当作已经验证过的代码接口。[附录 H，PDF 第 20–21 页](https://arxiv.org/pdf/2312.04511v3#page=20)

因此，LLMCompiler 的适用范围不止“一次把全部问题并行做完”。一轮内部可以有并行与顺序依赖，多轮之间可以有观察反馈。真正的限制是每一轮生成的关系是否正确，以及有多少时间能够被重叠。

## 重构耗时公式：加速比需要哪些假设

附录 E.1 先讨论 N 个互不依赖的任务，并忽略调度开销。记 pᵢᴿ 为 ReAct 第 i 次分析和行动的生成时间，pᵢᶜ 为 Compiler 第 i 个计划项的生成时间，eᵢ 为第 i 个工具执行时间，单位均为秒。顺序方法每一步先生成再执行，因此原式（1）为：

```text
Tᴿ = ∑ᵢ₌₁ᴺ (pᵢᴿ + eᵢ)
每次规划与每次工具等待都进入总和。
```

非流式 Compiler 先写完计划，再启动全部独立任务，因此原式（2）为：

```text
Tᶜ = ∑ᵢ₌₁ᴺ pᵢᶜ + maxᵢ eᵢ
规划仍需时间，工具阶段等最慢的一项。
```

原式（4）把加速比定义为 γ=Tᴿ/Tᶜ。当工具时间远大于规划时间，且每项工具耗时相同，顺序执行要等 N 份、并行执行只等一份，加速比可接近 N。当规划时间占主导，而且两种方法的规划总时间相近，加速比就接近 1。[原式（1）–（6），PDF 第 16–17 页](https://arxiv.org/pdf/2312.04511v3#page=16)

这些是指定近似条件下的判断，不能读成任何系统都保证 1 至 N 倍。若新规划更昂贵、并发造成资源争用，或者新策略实际执行了更多工作，加速比可以小于 1。论文后面的 WebShop 正好提供实例。此外，这组简式没有单列最终汇总答案的时间；完整端到端分析必须计入它。

**原式（3）还有一个需要补充的条件。** 论文把流式时间写成全部计划生成时间加最后一个任务的执行时间：

```text
原式（3）：Tˢᶜ = ∑ᵢ₌₁ᴺ pᵢᶜ + e_N
```

它只有在最后生成的任务也最后完成时才成立。沿用“任务互相独立、生成即可启动、资源充足”的设定，第 i 个任务在前 i 项计划生成完时启动。因此更一般的表达应当取所有完成时刻的最大值：

```text
读者推导：sᵢ = ∑ⱼ₌₁ⁱ pⱼᶜ
T流式 = maxᵢ (sᵢ + eᵢ)
```

用两项任务即可检查。两项计划各生成 1 秒，两个工具分别执行 100 秒和 1 秒。第一项在第 1 秒启动、第 101 秒完成；第二项在第 2 秒启动、第 3 秒完成。真实总时间应为 101 秒，原式（3）却只算出 3 秒。非流式时间是 102 秒。这个反例是本章依据同一简化模型完成的条件核验，**不是复现作者系统**。[原公式页面，PDF 第 17 页](https://arxiv.org/pdf/2312.04511v3#page=17)

修正并不否定流式思路。在这些理想条件下，每个部分计划的生成时间都不超过完整计划时间，所以一般式仍不大于非流式时间。它说明的是收益必须看所有任务何时完成，而非只看最后发出的任务。

对于有依赖的图，还可进一步作教学推导：一项任务最早启动的时刻，是“自身计划已生成”与“所有上游已完成”两者中的较晚者。最终总时间不会短于最长依赖链。有限并发、接口限流和共享状态会增加额外约束。这里的推导帮助读者识别假设，论文并未逐一测完这些运行条件。

## 静态实验：究竟比较了什么

主实验的 HotpotQA 只使用开发集中的比较型子集，约 1500 题，典型结构是两次独立搜索后比较；不是整个多跳问答集。Movie Recommendation 有 500 题，每题给四部参考电影和四个候选，需要查询共八部电影。作者还构建了 113 题的 ParallelQA，涉及 56 个实体、最多 2 至 5 个并行分支以及不同汇合结构。题目由 GPT-4 生成后人工标注，并特意使用维基百科首段就能找到的属性，以减少搜索失败干扰。[§4.1、附录 I，PDF 第 5、7、21 页](https://arxiv.org/pdf/2312.04511v3#page=5)

这种设计让依赖安排更容易被单独观察，也意味着它不能代表现实中页面难找、结果相互冲突或信息过时的全部检索任务。

HotpotQA 与 Movie 使用 gpt-3.5-turbo-1106，ParallelQA 使用 gpt-4-turbo-1106。开源模型为 LLaMA-2 70B，以两张 A100 80GB 和 vLLM 提供服务。三个静态任务分别使用 3、1、5 个示范，不同方法使用相同示范问题。通常温度为 0，结果重复运行三次取平均；三次运行不等于三倍独立题目。API 静态实验发生在 2023 年 11 月，以下延迟属于这些历史条件。[附录 D，PDF 第 15–16 页](https://arxiv.org/pdf/2312.04511v3#page=15)

## 为什么八次搜索没有带来八倍加速

Movie 能并行查八部电影，却只实现约 3.74 倍加速。附录给出的解释比“并行有开销”具体：规划平均耗时 1.88 秒，最终回答平均 1.62 秒，二者合计已经超过 5.47 秒总延迟的一半。它们不会因搜索变成八路就自动除以八。最慢一次搜索平均需要 1.13 秒，而全部搜索的平均仅 0.61 秒，系统还要等较慢的那一次。[附录 E，PDF 第 16 页](https://arxiv.org/pdf/2312.04511v3#page=16)

这些阶段存在重叠，测量边界也不同，不能强行把各项均值简单相加，要求恰好等于端到端均值。能得出的稳妥结论是：可并行部分的占比、慢任务和串行收尾共同限制收益。

流式消融进一步把一种收益单独拿出来。HotpotQA 从非流式 4.00 秒降到 3.95 秒，Movie 从 5.64 降到 5.47 秒，ParallelQA 从 21.72 降到 16.69 秒。前三者对应约 1.01、1.03、1.30 倍。流式对执行较久的任务更有空间，但前两项只有很小的收益。[表 C.1，PDF 第 15 页](https://arxiv.org/pdf/2312.04511v3#page=15)

准确率改善也需要解释。Movie 中原始 ReAct 约 85% 的问题没有完成八次搜索就停止，Compiler 约 99% 完成八次。调整提示后，ReAct 准确率从 68.60% 升到 72.47%，仍低于 Compiler 的 77.13%。这支持“提前列完整任务减少遗漏”的解释，却不表明并行这个动作本身能让同样的信息更正确。[附录 A.1，PDF 第 13 页](https://arxiv.org/pdf/2312.04511v3#page=13)

LLaMA-2 的 HotpotQA 错误分析提供相反方向的细节：约 10% 的原始 ReAct 轨迹重复调用至少四次，这一组准确率低于 10%，Compiler 对同组约为 50%。但另有不到 3% 的题，ReAct 第三次改用实体别名搜索反而更好。多调用一次既可能是无效循环，也可能是有用的纠错，不能仅凭调用次数判断。[附录 A.2，PDF 第 14 页](https://arxiv.org/pdf/2312.04511v3#page=14)

ParallelQA 的分析把 36 个失败结果归到三个环节：规划约占 8%，工具执行约占 64%，最终回答约占 28%。规划错误实际为 3 个，常见原因是引用错编号；工具执行多为属性选择和单位问题；汇总多为比较错误。**这些百分比的分母是失败结果，不是全部题。** 36/（113×3）约为 10.6%，与三次重复运行的规模相符，因此不应自动把“36 examples”解释为 36 道互不重复的题。[附录 B，PDF 第 15 页](https://arxiv.org/pdf/2312.04511v3#page=15)

<a id="section-7"></a>
## 动态实验：每轮知道一点，再安排下一轮

24 点游戏要求四个数各用一次，通过四则运算得到 24。原例 2、4、4、7 可以组成 4×(7−4)×2。论文复用 Tree of Thoughts 的搜索思路：一个工具提出下一步候选状态，另一个评估这些状态继续成功的可能，再选出前五个状态向下搜索。下一轮扩展谁取决于上一轮筛选，因此不能一开始写出实际会走完的整棵树。[§4.2、附录 H–J，PDF 第 8、20–22 页](https://arxiv.org/pdf/2312.04511v3#page=8)

Compiler 的做法是并行处理当前轮的候选及评估，拿到筛选结果后重新规划下一轮。它改变了搜索流程的调用安排，没有据此证明一种全新的数学求解算法。

| 24 点，100 题 | ToT 成功率 / 秒 | LLMCompiler 成功率 / 秒 | 耗时比 |
| --- | ---: | ---: | ---: |
| GPT-4-0613 | 74.00% / 241.2 | 75.33% / 83.6 | 2.89 倍 |
| LLaMA-2 70B | 30.00% / 952.06 | 32.00% / 456.02 | 2.09 倍 |

WebShop 则展示了更明确的收益交换。系统先搜索商品，再并行查看通常约十个结果的属性、选项和功能，最后综合选择。它与容易过早购买的 ReAct 看见的信息量不同，因此不是单纯把同一组调用执行得更快。[§4.3、附录 J，PDF 第 8–9、22 页](https://arxiv.org/pdf/2312.04511v3#page=9)

在同为 500 题时，Compiler 比 ReAct 的成功率分别高 28.4、20.4 个百分点，耗时却分别增加约 75%、34%。它用更多探索换来了更高成功率，这是对“使用并行框架就一定更快”的直接反例。

论文强调相对 LATS 约 101.7 倍速度，其算式是 1066/10.48，分子来自 50 题、分母来自 500 题。按同为 50 题的两行回算约为 99.44 倍，仍是很大的报告差距，但题数一致也不自动证明样本和运行环境完全一致。还要注意，LATS 的平均得分 75.9 高于 Compiler 的 72.8，不能把成功率更高写成所有指标都更好。原文给 Compiler 得分的波动为 72.8±4.01，也不足以独立判定统计等价或显著性。

<a id="section-8"></a>
## 论文证明到哪里，下一项实验怎样更有辨别力

这篇论文的有力结论是：当调用依赖能被清楚表达，任务又包含独立分支时，让程序处理就绪条件和并发，可以减少重复启动模型及串行等待；流式执行与动态重规划扩展了可处理的结构。主实验、流式消融、24 点与 WebShop 分别支撑这条论证的不同部分。

边界同样具体。模型仍可能计划错关系、引用错结果或误解工具输入；数学执行器前端仍可能取错属性。性能取决于真实工作量、串行阶段和工具延迟。按数据依赖可并行，也未必代表涉及付款、写共享文件等现实副作用的操作可以安全并发。这些副作用与资源约束并非本论文已充分检验的对象。

**一个可证伪的后续问题**是：准确率收益有多少来自更完整的探索，有多少来自更好的调度与上下文组织？可以先固定一张人工确认的调用图、同样的工具输出和同样工作量，比较顺序、非流式并行、流式并行三种执行方式；随后接回真实模型规划器，把规划错、执行错、最终综合错分别记录。前一层隔离调度价值，后一层才观察自然语言规划增加了什么。

如果准确率优势在固定探索数量后消失，更支持“看了更多证据”的解释；如果固定证据内容后仍保留，才有理由进一步检查局部上下文是否减少干扰。这是研究设计建议，本次没有执行。原表和公式的局部不一致需要保留，但也不应据此抹掉其他有独立数据支持的结果。

## 读者自测

**1. 八次工具调用可以同时启动，为什么不等于八倍加速？** 先用正文的时间组成作答，再指出工具耗时不同时要等哪一项。

**答案**：规划、最终汇总和部分依赖步骤仍是串行的；并行工具阶段由最慢任务决定，不能用平均工具时间替代。只有工具耗时几乎占全部、彼此等长且无额外开销，才接近八倍。

**2. 为什么原式（3）需要“最后生成的任务最后完成”这个条件？** 请用 1 秒规划、100 秒执行的早发任务解释。

**答案**：最后发出的任务可能很快结束，早发慢任务仍未完成。应比较每项的“生成可用时刻＋执行耗时”，取最大值；正文反例的总时间是 101 秒，而非 3 秒。

**3. 能否引用 WebShop 宣称“Compiler 比 ReAct 快 101.7 倍”？**

**答案**：不能。该倍数相对 LATS，且使用了不同题数行的延迟。相对同为 500 题的 ReAct，Compiler 成功率更高、耗时也更长。方法名、样本规模和评价指标缺一不可。

**4. 程序按 DAG 无误执行，能否证明答案正确？**

**答案**：不能。图可能漏掉任务或引用错误，工具可能取错数值，最后模型仍可能比较错。执行关系正确，只保证遵守了模型给出的关系，并不证明关系忠实表达了原问题。
