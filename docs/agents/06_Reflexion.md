## 研究问题：重复尝试为什么常常只是重复犯错

一个能查询、移动或写代码的模型，可能完成许多动作，却在开头误判状态。例如它以为已经拿到杯子，接下来找灯、开灯，整个流程看似合理，实际从第一步便偏离了环境。重新开始而不保存经验，会把同一个错误再走一遍。传统强化学习可以用奖励调整参数，但大型模型的训练代价很高。

Reflexion 提出一个使用阶段的替代办法：把任务的成功或失败信号，与执行记录一起解释成文字经验，下次尝试时把经验提供给执行者。论文标题中的“语言强化学习”描述这种反馈驱动的行为调整，**没有实施神经网络权重的梯度更新**。所谓“语义梯度”是作者的类比，并不是求导得到的向量。[§1、§3，第 1–5 页](https://arxiv.org/pdf/2303.11366v4#page=4)

它与 Self-Refine 的连接在于都使用反馈；区别在于这里着重处理跨整次尝试的经验与环境行动。一次失败可以包含许多步骤，反思需要找出哪一步导致后续失败，这叫错误归因。归因可以错，因此“写下反思”与“学到正确经验”必须分别检验。

<a id="section-2"></a>
## 三个角色怎样形成下一次尝试

执行者 Actor 生成文字或动作；评价者 Evaluator 判断这次尝试的表现；反思者 Self-Reflection 根据轨迹、评价和旧经验提出改法。它们是功能角色，不要求三个不同训练出来的模型。评价者也不一定是语言模型，可以是环境规则、答案精确匹配，或运行测试得到的结果。

为把原文 §3 写清楚，以下采用讲义统一记法，而非逐字照搬伪代码：

```text
τ_t ← Execute(M_a, task, mem_t)
r_t = M_e(τ_t)
sr_t = M_sr(τ_t, r_t, mem_t)
mem_(t+1) = 最近 Ω 条(mem_t 加入 sr_t)
```

τ_t 包含一次尝试的动作和观察；r_t 是任务评价，sr_t 是一段文字建议；Ω 是保留的经验条数，原文通常取 1–3。执行者在同一次尝试内看完整近期轨迹，跨尝试保留压缩后的经验。前者有细节但占上下文，后者更短却可能丢掉条件。压缩是否有帮助，不能仅用字数衡量。

以附录 B 的真实轨迹为例：任务是拿杯子在台灯下查看。第一次模型在 desk 1 发现杯子与灯，拿杯子后却转去 desk 2，随后对不在当前位置的灯反复执行操作，得到“没有发生变化”。反思记录灯在 desk 1，第二次直接去 desk 1 拿杯子、开灯，成功。**最可靠的经验是位置与动作前提；反思中“应先找灯再找杯子”的归因只是一个解释。** 第二次成功并不能证明原先的任务分解顺序本身是唯一错误。[附录 B，PDF 第 13 页](https://arxiv.org/pdf/2303.11366v4#page=13)

实际系统应在成功或预算耗尽时结束。原文算法 1 的循环条件写为“未通过 or 未达最大次数”，按字面可能导致到达预算仍继续；正文讲的是有界重试。这里按正文解释意图，并指出伪代码不是可直接执行的正确实现。本文没有检查作者仓库是否采用同样条件。

<a id="section-3"></a>
## 三类实验获得的反馈不一样

ALFWorld 是 134 个文本交互环境。执行者采用 ReAct，重复同一动作与响应超过三轮，或超过 30 个动作时，启发式评价认为这次尝试有问题并触发重试；另比较模型评价。记忆保存最近三条经验。经过 12 次连续尝试，系统解决 130/134 个任务，即约 97.0%。这是**累计解决比例**，不能读成第一次接触陌生任务便有 97% 成功率。基线同样可以重试，才能区分单纯增加机会与保存经验的作用。[§4.1、图 3，第 5–6 页](https://arxiv.org/pdf/2303.11366v4#page=5)

HotpotQA 使用 100 个问题，区分只凭模型知识推理、提供正确上下文的 CoT(GT)，以及允许 Wikipedia 检索的 ReAct。重试之间由环境用正确答案计算精确匹配，向智能体提供成败信号。模型没有看到答案文本，**但获得了由答案计算的反馈**；部署到无人知道答案的开放问答，不能假定这种信号免费存在。图 4 的记忆消融进一步比较保留旧轨迹与保留反思：有反思者比只保留经历多约 8 个百分点。它支持压缩与解释可能有用，而不证明任意长记忆都更好。[§4.2、图 4，第 6–7 页](https://arxiv.org/pdf/2303.11366v4#page=7)

编程实验采取另一条路线。模型先生成测试，用语法树检查筛去语法无效的测试，最多选六个，然后运行候选程序，将结果用于下一轮反思。语法合法不等于测试断言正确，也不等于测试充分。最终提交的一个候选才用基准的隐藏测试评价，作者因此报告 pass@1。这个指标的“1”指最终评价一个候选，**不代表内部只生成一次代码**。[§4.3，第 7 页](https://arxiv.org/pdf/2303.11366v4#page=7)

## 同一张表里，成功与退步必须一起读

| 表 1 的任务 | GPT-4 基线 → Reflexion | 可以支持的结论 |
|---|---|---|
| HumanEval / Python | 80.1% → 91.0% | 此协议下提高 10.9 个百分点。 |
| HumanEval / Rust | 60.0% → 68.0% | 对最难 50 题的翻译子集，不能当成整个 HumanEval 的同条件比较。 |
| MBPP / Python | 80.1% → 77.1% | 降低 3.0 个百分点，是反思流程可能伤害结果的重要反例。 |
| MBPP / Rust | 70.9% → 75.4% | 在另一任务语言组合中有提升。 |
| LeetcodeHard / Python | 7.5% → 15.0% | 在论文新建的 40 道难题集合上从约 3 题到 6 题；相对翻倍不等于可靠完成多数难题。 |

为什么同一套方法在 MBPP Python 退步？表 2 检查内部测试误判。正文讨论的是条件概率 P(最终答案错｜内部测试全过)：MBPP Python 为约 16.3%，HumanEval Python 约 1.4%。分母是内部测试通过的候选，而不是全部错误程序；不能把它套成常见分类表中另一种分母的“假阳性率”。内部测试漏掉错误，就会使系统过早宣布完成，反思根本没有机会启动。[表 1–2，第 7–8 页](https://arxiv.org/pdf/2303.11366v4#page=8)

表 3 在 HumanEval Rust 的 50 题子集上做了更有解释力的拆解：基线 60%，有反思但没有测试生成 52%，有测试但省去反思 60%，两者都有 68%。这个结果说明：在该设定中，只有反馈或只有解释都不够；没有检测依据的反思还会把正确程序改坏。但不能据这 50 题断言所有直接利用编译日志的方法都无效，作者的广泛表述应限于实际对照。

附录 A 的另一模型 starchat-beta 在 HumanEval Python 上，基线和 Reflexion 都约 26%。这约束了“给任何模型加反思就能提高”的说法；执行者理解反馈的能力同样重要。[附录 A，第 12 页](https://arxiv.org/pdf/2303.11366v4#page=12)

## 这篇论文怎样改变系统设计判断

论文的强项是把执行、评价、经验三个部分拆开，又跨交互、问答、代码观察了收益与失败。它更有力地支持“可靠评价与可用经验共同改善有界重试”，而非“语言反思等价于通用学习”。经验可能把偶然成功错误归因给某个动作；任务变了，旧经验可能失效；只保留三条也可能忘掉已经排除的路线。

后续研究可固定总调用预算和评价信号，比较三种记忆：原始失败轨迹、模型反思、由明确失败证据约束的简短经验。对已见任务和环境发生变化的新任务分别测试，统计恢复成功、重复错误、被错误经验误导的比例。若第三种记忆主要改善迁移，便支持“经验中的可验证事实比叙事解释更稳定”；若优势只在同一任务重试存在，则要收窄“学习”的范围。这是待验证方案，本次没有执行。

**自测**：给问答机器人加入 Reflexion，首先缺的可能是什么？常常是可信的成败反馈。只有模型自己觉得答错了，不能等同于论文里由真实答案计算的精确匹配。
