看完九篇，容易产生一种冲动：先自动发现推理结构，再计划、并行执行、自我修改、反思、树搜索，最后多角色写报告。这样拼接并没有论文直接提供的证据。每增加一层，调用成本、错误来源和状态管理都会改变。更可靠的办法，是先定位任务最困难的一步，再找到真正对准它的方法。

本章给出跨论文的解释与教学推演，不声称执行了新的综合实验。不同论文的数字只在各章原条件下比较；这里不把它们排成一个跨数据集排行榜。

<a id="section-1"></a>
## 一、先区分四种不确定性

第一种是不知道事实。需要查证的答案藏在网页或工具中，模型自己反复想不一定会新增信息。ReAct 通过观察改变后续动作；STORM 系统地扩展调查问题。它们都使用外部资料，但前者研究一般推理与行动轨迹，后者研究写作前的信息收集。[ReAct](./01_ReAct.md)／[STORM](./09_STORM.md)

第二种是不知道过程。事实或题目已经给定，却容易漏步骤、选择不合适的推理方式。Plan-and-Solve 提示模型先规划再求解；Self-Discover 从自然语言推理模块中选择、改写并组织出结构。它们都可能让过程更明确，却没有因为“有结构”就自动保证每一步执行正确。[Plan-and-Solve](./02_Plan_and_Solve.md)／[Self-Discover](./08_Self_Discover.md)

第三种是已有过程太贵。工具很多，顺序等待或反复读历史造成浪费。ReWOO 将计划、证据执行和答案汇总分开；LLMCompiler 把工具任务及依赖显式表示，调度可并行的部分。前者减少某些重复上下文，后者主要处理依赖与等待，两者不等同于“把所有调用同时发出去”。[ReWOO](./03_ReWOO.md)／[LLMCompiler](./04_LLMCompiler.md)

第四种是不知道当前方案是否足够好。Self-Refine 修改当前答案，Reflexion 从任务反馈总结后续尝试的经验，LATS 在多条候选轨迹间分配搜索。三者都需要评价，但评价来源、保存对象和改进单位不同。[Self-Refine](./05_Self_Refine.md)／[Reflexion](./06_Reflexion.md)／[LATS](./07_LATS.md)

这个区分能防止设计错位。事实缺失时，一味增加自我点评可能放大原有错误；工具完全独立时，让模型每拿到一个结果就重新计划可能徒增延迟；评价信号很不可靠时，扩大搜索可能更擅长寻找评价漏洞。

<a id="section-2"></a>
## 二、不要把同一个词背后的不同机制混在一起

| 常用词 | 论文中的具体含义 | 最容易混淆的地方 |
|---|---|---|
| 计划 | PS 的解题步骤；ReWOO 的证据占位符；Compiler 的任务依赖图 | 一段自然语言步骤不自动成为可正确调度的依赖图 |
| 反思 | Self-Refine 的本轮修改意见；Reflexion 的尝试间经验；LATS 的失败轨迹反馈 | 保存文字不等于更新权重，也不保证诊断原因正确 |
| 搜索 | ReAct 的外部资料搜索；LATS 的候选轨迹搜索 | 搜更多网页与搜索更多候选行动是不同计算 |
| 记忆 | 对话历史、结果引用、反思窗口、共享推理结构 | 不同对象的更新、失效和适用范围不同 |
| 成功 | 问答 EM、程序隐藏测试、环境任务、文章偏好 | 不能把各任务的百分比都叫准确率后直接横比 |

一个很实用的研究记录，是在画出方法流程后，为每条箭头写出传递的具体对象：原始网页还是摘要？工具结果还是占位符？失败奖励还是模型猜测？当输入对象写清，很多看似相同的模式就显出实质差别。

<a id="section-3"></a>
## 三、用一个调查任务推演计划与观察

设教学任务为：查明某家公司最近一次年报所列的营收、员工数及分部结构，并解释其同比变化。这个例子没有实际查询公司，也不提供现实财务建议，只讨论流程。

首先，不能在确认年报日期与版本前就填写“最近”。找到报告是后面多个步骤的共同依赖。找到以后，营收、员工数和分部表可能独立读取；同比变化还要对齐上年口径，不能只把两个数字相减。若报告说某部门已重分类，这个新观察会改变后续查询。

ReAct 可以逐步查报告、观察重分类说明，再调整下一步。它适合这种路线会被证据改变的情形，但若每个独立字段都必须走一轮完整思考和调用，成本会增加。ReWOO 可以先生成“报告→各项证据→汇总”的计划，用证据变量连接步骤；若关键分支事先未知，就需要检查其计划是否有恢复或重规划能力，不能靠占位符消除未知情况。

LLMCompiler 则让我们明确哪些任务真的可同时进行。教学设定：找报告耗时 2 秒；之后读取营收、员工数、分部表分别耗时 4、3、5 秒；最后统一检查 1 秒。忽略规划和调度开销，串行需要 2＋4＋3＋5＋1＝15 秒，按依赖并行的理想下界是 2＋max(4,3,5)＋1＝8 秒。这个 15/8＝1.875 倍是自定时长的演算，不是论文速度数据。

若营收读取结果决定还要下载重述文件，这条新依赖会改变关键路径。若服务只允许一次请求，三项读取也未必能并行。因而依赖图应表达信息、资源和实际副作用约束，而不只是把步骤排成好看的箭头。

STORM 对这个任务的启发，是在写解释之前收集不同方面的问题，比如规模变化、会计口径、业务结构。但它不自动提供财务专业判断。来源已经说明“分类调整”，模型仍可能写出“经营恶化导致下降”这一未经支持的因果关系。更全面的调查与更谨慎的推断必须同时存在。

<a id="section-4"></a>
## 四、用一个代码任务推演修改、反思与搜索

教学任务为编写函数：找出字符串中第一个只出现一次的字符，若没有则返回空结果。先生成代码，再请模型指出性能或边界问题，是 Self-Refine 类型的过程。这里如果没有执行程序，反馈仍来自模型对代码的判断。

若运行测试发现空字符串出错，并把“必须先处理空输入”保存给下一轮整体尝试，这是 Reflexion 类型的经验。可是一个通过当前测试的程序仍可能把大小写混为一谈，而需求并没有允许忽略大小写。错误或不完整的测试信号会让系统保留不恰当的经验。Reflexion 的 MBPP 负结果与自生成测试假阳性，正是不能省略的阅读内容。

LATS 类型的做法会保留多份候选或多个中间分支，用价值估计和访问次数选择值得继续探索的节点；它不是简单地把同一段错误代码改十遍。它还依赖能够比较、重置或重新执行状态的环境。生成代码时这一点相对容易，现实世界已经发出的邮件、完成的交易就不能像搜索树节点一样撤销。

这三种过程都应交代最后如何选答案。返回最后一轮、返回内部测试最好的一轮、返回外部验证成功的一轮，会得到不同结果与不同成本。如果用最终隐藏答案参与选择，却对外称完全独立的自我改进，研究结论就变了。各章会具体说明原文提供了什么信号，哪些算法描述还有歧义。

<a id="section-5"></a>
## 五、怎样设计公平的比较

跨论文讨论最容易忽视的是预算。让一种方法生成 50 个候选、另一种只生成 1 个，再只比较正确率，可以评估完整系统的最终效果，却不能单独证明候选组织方式更优秀。

一个面向明确研究问题的比较，可以固定基础模型版本、题目、工具及上下文可见信息，设置多个预算档位。在每个档位记录最终正确率、总 tokens、工具次数、总时间，并计入失败请求；然后比较质量与成本的曲线。这样既能问“同样预算谁更好”，也能问“达到同样质量谁更省”。这是一项建议的实验设计，本书没有运行。

反馈条件也需要固定。某些问答实验用标准答案判断本轮是否正确，某些代码实验只让模型看到自己生成的测试，某些环境直接提供成功奖励。如果一个方法获得可靠外部反馈，另一个只能自我判断，比较同时改变了方法和信息，不能把全部差异归给“反思”。

统计单位要与问题一致。100 个任务各重试 10 次，并不等于 1000 个独立任务；20 对文章由两人评判，也不是 40 个独立主题。应同时报告样本、随机性、重复运行与不确定性。论文未报告的部分不能由讲义补成已经做过的实验。

<a id="section-6"></a>
## 六、九篇之间真正有用的张力

**先计划与边做边看。** ReWOO、Compiler 表明提前组织过程可以降低某些成本；ReAct 展示新观察的重要性。它们并不逻辑矛盾，而是对“后续步骤能否提前确定”作出不同程度的依赖。值得研究的是在何种任务上、何时切换计划与观察，而不是给所有任务固定同一节奏。

**自我评价与外部证据。** Self-Refine 说明具体反馈在多个生成任务中有用，但数学等任务的收益和条件要细读；Reflexion 与 LATS 显示环境、测试与重试可以改变成功率，同时带来误判与预算问题。三篇合起来支持的结论是：评价信号应成为设计对象，而不只是一句“请反思”。

**结构正确与执行正确。** Self-Discover 的错误分析把部分失败归于结构生成、更多归于在给定结构下执行；STORM 的提纲覆盖提高也没有同步解决可核验性。这共同提醒我们，中间产物更规整，只是支持后续成功的一项条件。最终推理和事实关系仍需独立检查。

**平均提升与具体反例。** PS 的变量提取、ReWOO 的某些数据算术、Compiler 的 WebShop 延迟、Self-Refine 的任务差异、Reflexion 的 MBPP、Self-Discover 的部分 BBH 子任务和 STORM 的人工可核验性，都要求结论按实际证据收窄。保留这些结果，才能判断方法在什么条件下值得采用。

<a id="section-7"></a>
## 七、研究式自测：给选择写出可以被推翻的理由

**场景一：三个独立只读查询，答案只需拼成一张表。是否需要树搜索？**

参考答案：当前困难是独立调用的等待与汇总，显式依赖和并行已对准它。只有证据表明多候选搜索能解决真实选择难题，才有理由加入 LATS 类型机制。不能用论文整体成功率替代此任务上的理由。

**场景二：模型连续三次把同一段不可靠网页改写得越来越流畅。再加 Self-Refine 是否足够？**

参考答案：先检查缺少的是不是可靠事实来源。若没有新证据或能识别该错误的判定信号，自我修改可能只优化表达。更直接的研究问题是如何让冲突来源进入评价，以及评价是否真正改变错误断言。

**场景三：一个自动结构准备需三次调用，之后每个实例一次调用。只处理一题与一百题有什么不同？**

参考答案：在“同一结构可复用”的前提下，平均调用数是 1＋3/K，K＝1 时为 4，K＝100 时为 1.03。长度、耗时、质量还需另测；新实例若不再适合同一结构，不能继续无条件摊销。

**场景四：多次重试后成功率 97%，能否宣传首次成功率 97%？**

参考答案：不能。必须说明允许的尝试次数、停止规则和分母，同时报告首次成功率或完整曲线。Reflexion 的 ALFWorld 结果是学习这一边界的具体例子。

读到这里，你应能用一句完整的话描述设计选择：“因为任务的主要困难是 X，我选择改变 Y；预计能在相同 Z 条件下改善指标 W；如果出现反例 V，就需要重新判断。”这比背下九个模式名称更接近研究者实际工作的方式。
