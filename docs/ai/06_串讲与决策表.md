前五章分别讲了原理、上下文、RAG、Agent 和评测。这一章用一个具体需求把它们串起来，走一遍负责人从接到需求到上线要做的判断，最后给一张可以随时查的决策表。

案例是一个**教学例子**，数字是为了说明思路而设定的。

<a id="section-1"></a>
## 一、需求：一个“合同问答助手”

> 法务部每天被业务同事问很多合同问题：“这份合同的付款期限是多少天？”“违约金条款怎么写的？”“这个客户以前签过类似条款吗？”希望做一个 AI 助手，业务同事上传或选择合同后直接提问。

<a id="section-2"></a>
## 二、第一步：这件事适合用大模型吗？

先问三个问题：

| 问题 | 本案例的回答 | 对应章节 |
|---|---|---|
| 输入和输出是不是非结构化的文字？ | 是，合同是长文本，问题是自然语言 | 第 01 章 |
| 出错的代价有多大？ | 中等偏高：答错付款期限可能造成损失 | 第 01 章（幻觉）、精读四 |
| 能不能让人核对？ | 能：要求每个回答都标出合同原文出处 | 第 03 章 |

结论：适合，但必须**基于原文回答、标注出处、允许说“没找到”**。

<a id="section-3"></a>
## 三、第二步：模型怎样“知道”合同内容？

| 情况 | 方案 | 理由 |
|---|---|---|
| 问的是**当前这一份**合同（通常几千到几万 token） | 直接把整份合同放进上下文 | 小于 20 万 token 时可以不用 RAG（第 03 章）；配合提示缓存，追问时成本很低（第 01 章） |
| 问的是**历史上所有合同**（几千份） | RAG：切块、向量 + 关键词混合检索、重排序 | 资料太多放不下；合同编号、条款号这类内容需要关键词检索（第 03 章） |

注意第 02 章和精读一的提醒：即使一份合同放得下，**关键条款在长文中间时也可能被忽略**。所以要做一次“位置测试”：把同一个问题的答案条款放在合同的开头、中间、结尾，看准确率是否稳定。

<a id="section-4"></a>
## 四、第三步：提示词怎么写？

按第 02 章“合适的高度”：

- **角色和目标**：你是法务助理，帮业务同事查找合同中的具体条款。
- **原则**：只根据提供的合同回答；每个结论都要引用条款编号和原文；合同中没有相关内容时，明确说“合同中未找到”，并建议联系法务。
- **输出格式**：结论 + 原文引用 + 条款位置（便于程序展示和核对）。
- **示例**：3 个有代表性的问答，其中一个是“合同中没有相关条款”的情况。
- **顺序**：系统提示和合同全文放在前面（可以命中缓存），用户的问题放在最后。

<a id="section-5"></a>
## 五、第四步：要不要做成 Agent？

| 需求 | 方案 | 对应模式（第 04 章） |
|---|---|---|
| 查一份合同里的条款 | 一次调用就够 | 不需要 Agent |
| “这个客户以前签过类似条款吗？” | 先检索历史合同，再对比 | **提示链**：检索 → 对比 → 总结 |
| 按问题类型分别处理（条款查询、风险提示、起草建议） | 先分类再分流，简单问题用小模型 | **路由** |
| “把这份合同和公司标准模板逐条比对，列出所有差异” | 拆成多个子任务并行，再汇总 | **并行** 或 **编排者-工作者** |

结论：先用工作流，**暂时不需要自主 Agent**。如果以后要让它“直接修改合同并发给客户”，那就涉及真实后果，必须加人工确认（第 04 章护栏）。

<a id="section-6"></a>
## 六、第五步：怎么知道它好不好？

按第 05 章：

1. **建评测集**：请法务挑选 100 个真实问题，覆盖付款、违约、保密、终止等类型，其中约 15 个是“合同中没有答案”的问题。为每个问题写好正确答案和条款位置。
2. **二元判断**：每个回答检查三项——结论对不对、引用的条款对不对、没有答案时有没有如实说明。
3. **单独统计三个数**：准确率、错误率、合理拒答率（精读四）。设定上线标准，例如“错误率低于 3%，没有答案的问题中至少 90% 如实说明”。
4. **错误分析**：第一版跑完后，读完所有错误记录，归类计数，按数量从多到少修。
5. **模型评审**：如果要用模型评审自动打分，先用法务标注的 100 条校准，并且对“哪个回答更好”这类比较调换顺序评两次（精读三）。

<a id="section-7"></a>
## 七、第六步：算一算成本

按第 01 章的公式，设定一组教学数字：每次提问输入 1.5 万 token（合同 1.4 万可缓存，问题和历史 1 千），输出 500 token；输入单价每百万 token 3 美元，缓存按 0.1 倍计，输出每百万 token 15 美元。

- 未缓存输入：1,000 × 3 / 1,000,000 = 0.003 美元
- 缓存输入：14,000 × 0.3 / 1,000,000 = 0.0042 美元
- 输出：500 × 15 / 1,000,000 = 0.0075 美元
- **合计约 0.015 美元/次**；每天 2,000 次，约 30 美元/天。

如果第一次读合同时没有缓存，那一次的输入是 15,000 × 3 / 1,000,000 = 0.045 美元。同一份合同连续追问，缓存的价值就体现出来了。

<a id="section-8"></a>
## 八、决策表：什么情况用什么方法

| 你遇到的情况 | 优先考虑 | 不推荐 | 依据 |
|---|---|---|---|
| 模型需要知道公司内部、经常更新的资料 | RAG；资料少时直接放进上下文 | 微调 | 第 03 章 |
| 模型需要固定的输出格式或风格 | 提示词 + 示例；结构化输出；再不行考虑微调 | 写几十条规则 | 第 02、03 章 |
| 回答经常编造冷门事实 | 提供资料或工具；允许并鼓励说“不知道”；评测中给答错扣分 | 只在提示词里写“不要编造” | 第 01 章、精读四 |
| 长提示词里的关键信息被忽略 | 重排序，把关键内容放在开头或结尾；删掉无关内容 | 继续加长上下文 | 第 02 章、精读一 |
| 需要多个步骤，但步骤是固定的 | 工作流（提示链、路由、并行） | 自主 Agent | 第 04 章 |
| 步骤无法预先确定、需要灵活决策 | Agent，加步数上限、日志和人工介入点 | 没有护栏的 Agent | 第 04 章、精读二 |
| Agent 会执行写入、付款、对外发送 | 人工确认；限制权限和范围；检查“致命三要素” | 完全自动化 | 第 04 章 |
| 不知道改动是变好还是变坏 | 评测集 + 错误分析 | 试几个例子凭感觉 | 第 05 章 |
| 想用模型自动评分 | 先用人工标注校准；成对比较调换顺序 | 直接相信评审分数 | 第 05 章、精读三 |
| 成本太高 | 固定内容放前面以命中缓存；控制历史长度；简单任务路由到小模型 | 盲目换最便宜的模型 | 第 01、04 章 |
| 有新模型发布，便宜一半 | 用现有评测集跑一遍再决定 | 直接切换 | 第 05 章 |

<a id="section-9"></a>
## 九、负责人的技术方案评审清单

拿到团队的 AI 功能技术方案时，逐条问：

1. **成功标准**：怎样算做好了？有没有评测集？上线标准是什么？
2. **知识来源**：模型靠什么知道答案？精确、冷门的事实是不是来自资料或工具，而不是模型记忆？
3. **上下文**：每次调用放了哪些内容？有没有放多？关键信息在哪里？能命中缓存吗？
4. **出错时**：能不能说“不知道”？用户怎样核对？出错时有没有日志可以排查？
5. **自动化程度**：哪些动作有真实后果？哪里有人工确认？
6. **成本**：每次调用大约多少钱？每天多少次？用户量翻十倍时怎样？
7. **换模型**：如果要换模型，用什么证明新模型更好？
