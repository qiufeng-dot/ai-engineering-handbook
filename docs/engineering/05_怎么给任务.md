第 03、04 章的结论可以浓缩成一句话：**Codex 会认真执行你写下的东西，也会自作主张地填补你没写的东西。**这一章把这句话变成可直接使用的方法：一个任务说明模板、一套“先计划还是直接做”的判断规则，以及一份精简的 AGENTS.md 范本。

<a id="section-1"></a>
## 一、任务说明的四个基本要素

OpenAI 的 Codex 最佳实践建议每个任务包含四个部分：

| 要素 | 回答的问题 | 缺了会怎样 |
|---|---|---|
| **目标**（Goal） | 要改变或做出什么？ | 它会按自己理解的目标去做 |
| **上下文**（Context） | 相关的文件、文档、例子在哪？ | 它会到处翻找，可能改错地方 |
| **约束**（Constraints） | 必须遵守什么标准和限制？ | 它会按“通常做法”引入你不想要的东西 |
| **完成标准**（Done when） | 怎样才算做完？ | 它会在“看起来做完了”时停下，或无休止地补充 |

官方的说法是，这样能让 Codex“保持在范围内、少做假设、产出更容易审查的结果”。

根据第 04 章的研究，再补三个要素，专门对付跑偏和过度测试：

| 补充要素 | 对付的问题 | 依据 |
|---|---|---|
| **不做什么**（Out of scope） | 顺手重构、顺手加功能、改无关文件 | Google 审查规范：解决现在需要解决的问题，不解决猜测中将来可能出现的问题 |
| **测试要求**（具体到类型和数量） | 过度测试或测试不足 | AGENTS.md 研究：“多测试”的指令会被彻底执行 |
| **出口条款**：不需要改、或遇到矛盾时怎么办 | 行动偏差、为通过测试而作弊 | FixedBench：明确“不动手也算成功”后正确率从 60.5% 升到 88.5%；ImpossibleBench：允许中止后作弊率从 54% 降到 9% |

<a id="section-2"></a>
## 二、可直接复制的任务模板

```markdown
## 目标
<一两句话：要实现什么，给谁用，为什么需要>

## 上下文
- 相关文件：<路径>
- 参考已有写法：<某个类似功能的文件>
- 背景信息：<业务规则、用户反馈原文、错误日志>

## 约束
- 不新增第三方依赖（如确实需要，先停下说明理由）
- 遵循 <某个文件> 的现有写法
- <性能、安全、兼容性等要求>

## 不做什么
- 不修改 <某些目录/文件>
- 不做与本任务无关的重构、重命名、格式调整
- 不修改已有测试的期望值；如果认为已有测试是错的，停下来告诉我

## 测试要求
- 为 <具体行为> 写单元测试，覆盖：<正常情况>、<边界情况 1>、<边界情况 2>
- 只运行相关测试：<命令>；完成前再运行一次完整测试：<命令>
- 不需要端到端测试 / 需要 1 个端到端测试覆盖 <主流程>

## 完成标准
- <可检查的结果 1>
- <可检查的结果 2>
- 上述测试命令全部通过，并在回复中贴出命令和输出

## 出口条款
- 如果发现问题已不存在或不需要修改，不要改代码，说明证据即可，这算完成。
- 如果需求与现有代码或测试矛盾，停下来列出矛盾点问我，不要自行取舍。

## 交付
- 在新分支上完成，开一个 PR
- PR 说明包括：改了什么、为什么、没做什么、怎么验证的
```


不是每个任务都要填满。改一行文案时，“目标 + 完成标准”两行就够了。**任务越大、越模糊、风险越高，填得越全。**

<a id="section-3"></a>
## 三、写好“完成标准”：用 Given / When / Then

“完成标准”是整个模板里最重要的部分，也是最容易写虚的部分。“功能正常工作”“体验良好”都不是标准，因为没法检查。

行为驱动开发（BDD）的提出者 Dan North 在 2006 年给出了一个写验收标准的格式，后来成为行业通用写法：

```text
Given（假定）  某个初始情况
When （当）    发生某个事件
Then （那么）  应该出现某个结果
```


**例子**：给 AI 聊天应用加“导出对话为 Markdown”。

| 写法 | 能检查吗？ |
|---|---|
| “用户可以导出对话。” | 不能：导出成什么？在哪里点？空对话呢？ |
| Given 一段包含 3 轮问答的对话，When 用户点击“导出”，Then 下载一个 `.md` 文件，每轮问答以 `**用户**：` 和 `**助手**：` 开头，按时间顺序排列 | 能 |
| Given 一段空对话，When 用户点击“导出”，Then 按钮不可点击，并提示“暂无内容可导出” | 能 |
| Given 对话里有代码块，When 导出，Then 代码块保持原格式 | 能 |

这三条 Then 直接就是测试要覆盖的行为。**你写出了验收标准，就同时决定了“该写哪些测试”**——Codex 不需要自己猜测试范围，也就不容易过度测试。

<a id="section-4"></a>
## 四、先计划，还是直接做？

Anthropic 的 Claude Code 文档给了一条很好记的判断标准：**如果你能用一句话描述要改的 diff，就跳过计划。**计划在以下情况最有用：不确定该怎么做、改动涉及多个文件、不熟悉要改的代码。

| 情况 | 做法 |
|---|---|
| 改文案、改一个配置值、加一条日志 | **直接做**，一两句话的任务说明 |
| 修一个能描述清楚的 bug | **先证据后修**：要求它先重现（写一个失败的测试），确认后再修 |
| 新功能，你知道要什么，但不知道怎么实现 | **先计划**：用计划模式（或要求“只出计划不改代码”），你审完计划再让它做 |
| 新功能，你自己也没想清楚要什么 | **先访谈**：让它向你提问，把答案整理成规格文档（SPEC.md），再开**新会话**按规格实现 |
| 大改动、跨很多文件、影响其他人 | **拆小**：按计划拆成多个小任务，每个任务一个 PR |
| 只是想了解代码怎么工作 | **只问不改**：只读模式下提问 |

### 审计划时看什么

计划是你最便宜的纠偏机会：改计划只需改几行字，改代码要返工。审计划时只问五个问题：

1. 它理解的目标和你的一致吗？
2. 要改的文件清单里，有没有你觉得不该动的？
3. 有没有你没要求的步骤（“顺便优化一下……”）？
4. 测试计划是不是对应你的验收标准，没有多出一大堆？
5. 有没有新增依赖、数据库结构变更、删除数据这类高风险动作？

<a id="section-5"></a>
## 五、任务的大小

Google 的代码审查规范建议：一次改动**只做一件事**；大约 100 行通常是合适的大小，1000 行通常太大；如果拿不准，就写得比你认为需要的更小。原因：小改动审得更快、审得更仔细、引入的 bug 更少、出问题时更容易撤回。

这条规则对 Codex 同样适用，而且更重要：**你审查能力有限，每次交给它的任务就应该小到你能审得过来。**一次产出 2000 行改动的任务，你实际上无法审查，只能选择相信或不信。

拆分方法（同样来自 Google 规范）：

- **纵向拆**：按用户能感知的小功能拆，比如“先导出纯文本，再支持代码块，再加按钮状态”。
- **横向拆**：先做底层共用部分，再做上层。
- **把重构和功能分开**：“整理旧代码”和“加新功能”永远是两个任务。

<a id="section-6"></a>
## 六、团队的 AGENTS.md：短而具体

结合官方建议和第 04 章研究，一份好的 AGENTS.md 只写 Codex **猜不出来**的东西。下面是一个范本，大约 30 行：

```markdown
# 项目约定（给 AI 代理）

## 命令
- 安装依赖：uv sync
- 运行相关测试：uv run pytest tests/<模块名> -q
- 完成前运行：uv run pytest -q && uv run ruff check .

## 测试策略
- 修 bug：先写一个能重现问题的失败测试，再修复。
- 新业务规则：为每条验收标准写单元测试，加必要的边界情况。不为没有逻辑的代码写测试。
- 端到端测试只在任务明确要求时添加。
- 不修改已有测试的期望值；如果认为测试有误，停下说明。

## 边界
- 不新增依赖，除非任务明确允许。
- 不修改 migrations/ 和 .github/ 目录。
- 不做任务之外的重构、重命名或格式调整。

## 提交与 PR
- 每个任务一个分支，分支名：<类型>/<简短描述>，如 fix/login-timeout
- PR 说明必须包括：改了什么、为什么、没做什么、验证命令及结果。

## 出口
- 发现问题已不存在、需求有矛盾、或需要越界时，停下来说明，不要自行决定。
```


**维护方法**：Codex 反复犯同一个错误时，加一条规则；某条规则删掉后它的行为不变，就删掉。每次修改后观察几次任务，确认行为真的变了。

## 七、一个前后对比

**原来的写法**（容易跑偏）：

> 帮我优化一下登录功能，现在用户经常反馈登录有问题，记得写测试。

问题：“优化”没有边界；“有问题”没有证据；“记得写测试”会被理解为“多写测试”；没有说完成标准，也没有出口。

**改进后的写法**：

> **目标**：修复“会话超时后再次登录失败”的问题（用户反馈原文见下）。
> **上下文**：登录逻辑在 `src/auth/`，重点看令牌刷新部分。用户反馈：“页面放了半小时，再点登录就一直转圈。”
> **先证据**：先写一个测试重现这个问题（模拟会话超时后登录），确认它失败。如果无法重现，停下来告诉我你试了什么，不要改代码。
> **不做什么**：不改登录页面样式，不重构其他认证代码，不新增依赖，不修改已有测试。
> **测试要求**：只新增重现这个问题的测试，以及必要的 1–2 个边界情况（例如刚好在超时时刻）。
> **完成标准**：新测试修复前失败、修复后通过；`uv run pytest tests/auth -q` 全部通过，贴出输出。
> **交付**：新分支 `fix/login-timeout`，开 PR，说明根本原因。

## 自测

<details>
<summary>1. “测试要充分”和“为三条验收标准各写一个单元测试，加上价格为 0 的边界情况”有什么本质区别？</summary>

前者没有可检查的终点，Codex 会按自己的理解尽量多写（研究显示它会认真执行这类指令）；后者明确了测试的范围和数量，完成与否一目了然，也直接对应你关心的行为。
</details>

<details>
<summary>2. 你想加一个新功能，但自己也没想清楚交互细节。应该直接让 Codex 开始做吗？</summary>

不应该。先让它向你提问（访谈），把答案整理成规格文档；确认规格后，开一个新会话按规格实现。直接开做会让它替你做产品决定。
</details>

<details>
<summary>3. 为什么“出口条款”很重要？举两种它要处理的情况。</summary>

代理有行动偏差，也会为了通过检查走捷径。出口条款告诉它停下来是合法的。两种情况：问题已经不存在（不应修改代码）；需求与现有测试或代码矛盾（不应自行修改测试或做取舍）。
</details>

<details>
<summary>4. 判断：下面这个任务该“直接做”还是“先计划”？“把首页标题从‘欢迎’改成‘欢迎使用 XX 助手’。”</summary>

直接做。改动能用一句话描述，范围清楚，风险低。完成标准就是“首页标题显示为新文字，现有测试通过”。
</details>
