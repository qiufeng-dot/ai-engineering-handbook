审查 Codex 的产出，不等于逐行读懂代码。作为负责人，你要判断的是四件事：**它做的是不是我要的？有没有做我没要的？它说的“完成”有没有证据？哪些部分需要懂技术的人再看？**这四件事都可以通过“看变化、问问题、亲手试”来完成。

<a id="section-1"></a>
## 一、审查的标准：更好，而不是完美

Google 的代码审查规范给出的核心标准是：只要一个改动**明确改善了系统的整体代码健康**，即使不完美，审查者也应该倾向于批准。原话是：没有“完美”的代码，只有“更好”的代码。

这个标准对你有两层意义：

1. 不要因为“可能还能更好”而让 Codex 一轮轮修改。每一轮修改都可能引入新的跑偏。
2. 但“明确改善”是底线：引入了你没要求的东西、或者没有证据证明它有效，就没有达到底线。

Anthropic 的文档还提醒了一个反方向的陷阱：如果你让另一个 AI 去“找问题”，它几乎总能找到一些，即使代码没问题；**照单全收会导致过度设计**——多余的抽象层、防御性代码、针对不可能发生情况的测试。所以审查意见要分级：只有影响正确性或违背需求的问题必须改，其余是可选的。

## 二、五步审查流程

![图 6-1　五步审查流程。前四步每次都做，合计约 20–35 分钟；第五步用于高风险改动。](../../assets/engineering/06_review_flow.svg)

图 6-1　五步审查流程。前四步每次都做，合计约 20–35 分钟；第五步用于高风险改动。

### 第 ① 步：读汇报，先找证据

好的汇报应该包括：改了什么、为什么、**没做什么**、怎么验证的（**附命令和输出**）。Anthropic 的建议是：让代理**展示证据，而不是声称成功**——测试输出、执行的命令和结果、截图。审查证据比自己重新验证快得多。

如果汇报只有“已完成，所有测试通过”，第一个要求就是：“贴出你运行的测试命令和完整输出。”

### 第 ② 步：看变化清单（diff 统计）

这是性价比最高的一步。对着第 01 章学的 diff 统计，逐行问：

| 看到什么 | 问什么 |
|---|---|
| 一个和任务无关的文件被修改 | “这个文件为什么要改？任务里没有提到它。” |
| 依赖文件变化（`package.json`、`pyproject.toml`、锁文件） | “新增或升级了什么依赖？为什么不用现有的？” |
| 配置、CI、部署文件变化（`.github/`、`Dockerfile`、`.env.example`） | “为什么要改构建或部署配置？” |
| 数据库迁移文件（`migrations/`） | 高风险，必须请懂数据库的人审 |
| 大量删除（几百行 `-`） | “删了什么？有没有删掉别人还在用的功能？” |
| 改动总量远超预期（你以为 50 行，实际 800 行） | 很可能范围失控，考虑丢弃重做（见第五节） |

### 第 ③ 步：专看测试改动

这一步专门对付“过度测试”和“假测试”。分两类看：

**新增的测试——是否过度？**

1. 让 Codex 列出每个新测试保护的是哪条行为，对照你的验收标准。对应不上的，问“这个测试为什么需要”。
2. 看测试名字。好名字读起来像业务规则（“空对话不能导出”）；描述内部步骤的名字（“test_calls_formatter_before_writer”）是变化探测器的信号（第 02 章）。
3. 看比例：业务代码改了 20 行，测试新增 400 行，要问清楚。
4. 看是否新增了端到端测试、是否大量使用替身（mock）。

**被修改、删除、跳过的已有测试——是否作弊？**

这比“测试太多”严重得多，必须逐条确认：

| 危险信号 | 可能意味着 |
|---|---|
| 已有测试的**期望值**被改了 | 可能是把标准改成迎合错误的程序输出 |
| 测试被删除，或加了 `skip` / `xfail` / `@pytest.mark.skip` / `.skip(` | 让失败的测试“消失” |
| 业务代码里出现针对特定输入的分支，比如 `if user_id == "test_user":` | 专门为测试写的特例（ImpossibleBench 中的“特殊处理”） |
| 大段 `try ... except: pass` 之类“吞掉错误”的代码 | 让报错消失而不是解决问题 |
| 测试里断言被放宽，比如从“等于 90”变成“大于 0” | 降低标准 |

Kent Beck（测试驱动开发的提出者）在 2025 年记录自己用 AI 编程的经验时，把“**作弊：禁用或删除测试**”列为 AI 跑偏的三个警告信号之一，另外两个是**陷入循环**和**添加没被要求的功能**。

### 第 ④ 步：亲手验证行为

自动化测试再多，也替代不了你作为“第一个用户”试一遍。Simon Willison 在描述负责任地使用 AI 编程时，专门把**人工质量检查**列为必要技能。具体做法：

- 让 Codex 给出“手动验证步骤”：如何启动、点哪里、预期看到什么。
- 按你的验收标准（Given/When/Then）逐条试一遍，尤其是边界情况（空输入、超长输入、网络断开）。
- 有界面的改动，要求截图对比。

### 第 ⑤ 步：独立复审

- **独立 AI 复审**：开一个**新会话**（或用 Codex 的 `/review`），只给它 diff 和需求，让它检查“每条需求是否实现、范围外是否有改动、列出的边界情况是否有测试”。新会话没有看过写代码时的推理，不会偏袒自己写的代码。复审指令里要写明：**只报告影响正确性或违背需求的问题**，避免过度设计。
- **请技术同事审**：以下改动必须有懂技术的人看——身份认证与权限、支付和金额计算、数据删除与数据库结构变更、密钥与安全配置、性能关键路径、对外公开的接口。

<a id="section-3"></a>
## 三、跑偏信号速查表

| 类别 | 信号 | 下一步 |
|---|---|---|
| **范围** | 改了任务没提到的文件；“顺便”重构、改名、调格式 | 要求撤回范围外改动，或拆成单独任务 |
| **功能** | 加了你没要求的功能、配置项、参数 | 问“需求里哪一条要求了这个？”，没有就删 |
| **结构** | 为一个小功能新建了好几层抽象、通用框架 | 要求“用最简单的方式实现当前需求” |
| **依赖** | 新增第三方库 | 要求说明理由和替代方案 |
| **测试量** | 测试远多于验收标准、端到端测试过多、替身过多 | 要求逐个说明价值，删除对应不上需求的 |
| **测试真实性** | 改期望值、删除或跳过测试、特例代码、吞掉错误 | 拒绝，要求恢复测试并解释 |
| **过程** | 反复绕圈、同一错误改了好几轮 | 停止，开新会话，改写任务说明 |
| **汇报** | 只有“完成了”，没有命令输出和证据 | 要求贴出证据 |

<a id="section-4"></a>
## 四、可以直接发给 Codex 的审查问题

```text
1. 列出你修改的每个文件，每个文件一句话说明修改原因，并标出哪些修改不在任务要求里。
2. 你是否修改、删除或跳过了任何已有测试？逐条列出并解释原因。
3. 列出你新增的每个测试，说明它保护的是哪条验收标准。哪些测试可以删掉而不降低对需求的保障？
4. 是否新增或升级了依赖？如果有，为什么现有依赖不能满足？
5. 贴出你运行的测试和检查命令，以及完整输出。
6. 给我一份手动验证步骤：怎么启动，操作什么，预期看到什么。
7. 这个实现中你最不确定的地方是哪里？
```


第 3 问对过度测试特别有效：让它自己指出可删的测试，通常比你逐个判断快。第 7 问常常能暴露它自己也没把握的假设。

<a id="section-5"></a>
## 五、什么时候丢弃重做

不是所有产出都值得修。以下情况，**丢掉这个分支、改写任务说明、开新会话重做**通常比一轮轮修补更快：

- 改动量是预期的好几倍，范围明显失控。
- 它对需求的理解从一开始就错了。
- 已经纠正两次以上，仍在同一个问题上打转（Anthropic 的建议）。
- 你发现自己读不懂它的方案，也说不清它为什么要这样做。

丢弃的成本很低：分支没合并，主线不受影响（第 01 章）。真正的成本是**沉没成本心理**——“它已经写了这么多”。记住，下一次用更好的任务说明重来，通常一次就对。

<a id="section-6"></a>
## 六、把审查结果反馈到源头

每次审查发现的问题，问一句：**这个问题能不能在任务说明或 AGENTS.md 里提前预防？**

| 审查中反复出现的问题 | 加到哪里 |
|---|---|
| 总是顺手重构 | AGENTS.md 边界：“不做任务之外的重构” |
| 总是新增依赖 | AGENTS.md 边界：“不新增依赖，除非任务允许” |
| 测试写得过多 | AGENTS.md 测试策略写具体；任务模板写明测试范围 |
| 修改已有测试 | AGENTS.md + 技术手段：分支保护、测试目录需要特定人审批（第 08 章 CODEOWNERS） |
| 汇报没有证据 | AGENTS.md 提交与 PR 规则：“PR 说明必须包括验证命令及结果” |

这就是第 03 章说的维护方法：**观察到反复出现的错误，再加规则。**

<a id="section-7"></a>
## 自测

<details>
<summary>1. diff 统计显示改了 6 个文件，其中 `tests/test_price.py` 有 3 行修改、0 行新增。你最该问什么？</summary>

已有测试被修改了，要问：改了哪些断言？为什么改？如果是把期望值改成了程序当前的输出，而需求并没有变，那就是在降低标准，必须恢复。
</details>

<details>
<summary>2. 你请一个新会话复审，它列出了 12 条问题。应该全部让 Codex 改吗？</summary>

不应该。先分级：影响正确性、违背需求的必须改；风格偏好、假设性的未来需求、针对不可能发生情况的防御，都是可选的。全部照改会导致过度设计。最好在复审指令里提前要求“只报告影响正确性或需求的问题”。
</details>

<details>
<summary>3. 列出 Kent Beck 提到的 AI 跑偏的三个警告信号。</summary>

陷入循环；添加没被要求的功能（即使看起来合理）；作弊，例如禁用或删除测试。
</details>

<details>
<summary>4. 什么样的改动不能只靠你自己审，必须请技术同事？</summary>

身份认证与权限、支付和金额计算、数据删除与数据库结构变更、密钥和安全配置、性能关键路径、对外公开的接口。这些出错代价高，而且问题往往不会在简单的手动测试中暴露。
</details>
