前面十一章讲了大量方法。这一章把它们按“遇到什么情况”重新组织，方便你在实际工作中查。每一行都注明了出处章节，忘了原理时可以回去看。最后是一份负责人每周检查清单和六个综合练习。

<a id="section-1"></a>
## 一、给 Codex 派任务时

| 情况 | 方法 | 章节 |
|---|---|---|
| 改动能用一句话说清（改文案、改配置值） | 直接做；任务说明写目标和完成标准即可 | 05 |
| 修 bug | 先要证据：写一个能重现问题的失败测试；无法重现就停下报告 | 05、04 |
| 不确定问题是否还存在（老工单、别人可能修过） | 任务里写明“先确认问题是否仍存在，不存在则不修改，这算完成” | 04（FixedBench） |
| 新功能，知道要什么，不知道怎么做 | 计划模式出计划 → 你按五个问题审计划 → 再实现 | 05 |
| 新功能，自己也没想清楚 | 让 Codex 访谈你 → 写规格文档 → 新会话按规格实现 | 05、11 |
| 改动预计超过几百行或跨多个模块 | 拆成多个小任务，每个一个 PR | 05、08 |
| 想了解代码怎么工作 | 只读模式提问，不改代码 | 03 |
| 方向不确定，想比较几种方案 | 让它出 2–3 个方案的对比（或 best-of-N），只认真审选中的那个 | 11 |
| 重构旧代码 | 单独的任务和 PR，不与功能改动混在一起；要求行为不变、现有测试不改 | 05、08 |
| 改提示词、换模型 | 先跑评测集，附前后对比结果；用实验开关小范围上线 | 10 |

<a id="section-2"></a>
## 二、审查 Codex 产出时

| 你看到的情况 | 判断 | 处理 | 章节 |
|---|---|---|---|
| 汇报只说“完成了、测试通过” | 缺证据 | 要求贴命令和输出、手动验证步骤 | 06 |
| 改了任务没提到的文件 | 范围失控 | 问原因；范围外改动撤回或另开任务 | 06 |
| 新增依赖 | 风险 | 要求说明理由和替代方案 | 01、06 |
| 测试代码远多于业务代码 | 可能过度测试 | 要它逐个说明测试对应哪条验收标准，并指出哪些可删 | 02、06 |
| 已有测试被修改、删除、跳过 | 可能作弊 | 逐条确认；需求没变就拒绝 | 04、06 |
| 业务代码里针对特定输入写死结果 | 很可能在迎合测试 | 拒绝 | 04、06 |
| 新建多层抽象、“为将来准备”的通用框架 | 过度设计 | 要求用最简单方式实现当前需求 | 06、08 |
| 纠正两次还在绕圈 | 上下文被污染 | 停止，开新会话，改写任务说明 | 03、06 |
| 改动量是预期的好几倍 | 失控 | 丢弃分支，拆小重做 | 06 |
| 涉及认证、支付、删数据、数据库结构、密钥 | 高风险 | 必须请技术同事审 | 06 |

<a id="section-3"></a>
## 三、选择 AGENTS.md 内容时

| 想写的内容 | 写不写 | 理由 | 章节 |
|---|---|---|---|
| 构建、测试、检查的准确命令 | 写 | 它猜不出来 | 03、05 |
| 具体的测试策略（什么改动写什么测试） | 写 | 防止过度或不足 | 04、05 |
| 禁区（不能动的目录、不加依赖） | 写 | 防止范围失控 | 05 |
| 出口规则（矛盾时停下问） | 写 | 防止作弊和行动偏差 | 04、05 |
| 仓库结构概览、逐个文件介绍 | 不写 | 研究显示没有帮助，还增加成本 | 04 |
| “写高质量代码”“充分测试” | 不写 | 无法检验，“充分测试”会导致过度测试 | 03、04 |
| 用 `/init` 自动生成的长文件 | 精简后再用 | 研究显示自动生成的文件不提高成功率 | 04 |

<a id="section-4"></a>
## 四、团队流程选择

| 情况 | 方法 | 章节 |
|---|---|---|
| Web 应用或后端服务，随时可上线 | GitHub Flow，分支一两天内合并 | 08 |
| 要维护多个已发布版本（App、SDK） | 主线开发 + 发布分支 | 08 |
| 大功能要做好几周 | 拆小 + 功能开关，未完成的代码也能每天合并 | 08、10 |
| 需要固定节奏、相关方要定期看成果 | Scrum（两周冲刺） | 09 |
| 工作不断涌入、优先级常变 | 看板 + 在制品数量限制 | 09 |
| 代码写得快，但 PR 堆积等审查 | 限制“审查中”数量；改动更小；能自动化的交给 CI | 09、11 |
| 团队里没有资深工程师 | 更依赖机器强制：分支保护、CI、CODEOWNERS；高风险改动外请技术顾问审 | 08 |
| 重要技术选择（数据库、框架） | 写 ADR，并在 AGENTS.md 中引用 | 07 |
| 线上出事 | 先回滚或关开关恢复服务，再无责复盘 | 10 |
| 想知道 AI 到底有没有帮上忙 | 看 DORA 指标的趋势：吞吐量和不稳定性一起看 | 10、11 |

<a id="section-5"></a>
## 五、项目负责人每周检查清单

```markdown
## 交付
- [ ] 本周部署了几次？有几次需要回滚或紧急修复？（变更失败率）
- [ ] 有没有出问题后很久才恢复的情况？
- [ ] 有没有因为线上事故而做的计划外部署？（返工）

## 流程
- [ ] 待审查的 PR 有几个？最老的等了多久？（超过 1 个工作日要处理）
- [ ] 有没有存活超过 3 天的分支？
- [ ] main 本周有没有坏过？多久修好的？
- [ ] 超过 500 行的 PR 有几个？为什么没拆？

## AI 使用
- [ ] 本周审查中发现了哪些 Codex 跑偏？同类问题重复出现了吗？
- [ ] 有没有修改已有测试的 PR？都经过技术负责人批准了吗？
- [ ] AGENTS.md 需要加或删哪条规则？
- [ ] 改提示词或换模型的改动，都附评测结果了吗？

## 需求
- [ ] 下周要做的事，都有验收标准吗？（写不出验收标准的，先别交给 Codex）
- [ ] 进行中的工作是否超过了团队的在制品上限？
```

## 六、综合练习

每个练习先自己写答案，再展开参考答案。参考答案不是唯一正确的，重点看你是否用到了对应的原理。

<details>
<summary>练习 1：Codex 修一个“导出功能偶尔失败”的 bug，交回的 PR 改了 9 个文件、650 行，其中 420 行是测试，还升级了一个 PDF 库的主版本。你怎么处理？</summary>

1. 先看证据：有没有重现 bug 的失败测试？根本原因是什么？
2. 范围：9 个文件里哪些和导出有关？其余撤回或另开任务。
3. 依赖：主版本升级意味着不兼容改动（SemVer），这不应该混在 bug 修复里；问清是否必需，必需的话单独一个 PR 并请技术同事审。
4. 测试：420 行测试，要求逐个对应到行为，删掉对应不上的。
5. 如果解释不清，丢弃分支，用“先重现、不加依赖、只改导出模块、只写重现测试和 1–2 个边界测试”重写任务。
</details>

<details>
<summary>练习 2：你的 AGENTS.md 有 400 行，是半年前用 /init 生成后不断追加的。最近 Codex 每个任务都跑很久，测试一大堆。怎么改？</summary>

研究显示自动生成的上下文文件不提高成功率，却会增加探索、测试和成本，而且规则太多时重要规则会被淹没。逐行问“删掉它会让 Codex 犯错吗？”：删除仓库概览、通用原则、它能从代码看出来的内容；把“充分测试”这类话改成具体测试策略和命令（只跑相关测试）；保留命令、禁区、出口规则。改完后观察几次任务，确认行为确实变了。
</details>

<details>
<summary>练习 3：团队 4 人，大家各开 3–4 个 Codex 任务，每周产出 30 多个 PR，但上线的功能并没变多，线上问题反而增加了。诊断并给出调整方案。</summary>

诊断：瓶颈在审查和集成，不在编码；在制品过多；审查可能在走过场，导致不稳定性上升（符合 DORA 2025 的发现）。调整：设定在制品上限（尤其“审查中”）；PR 更小；用分支保护和 CI 强制检查；对测试改动、依赖变化设 CODEOWNERS；每周看变更失败率和返工率，确认调整是否有效。
</details>

<details>
<summary>练习 4：产品经理给的需求是“让聊天助手的回答更专业”。你准备怎么交给 Codex？</summary>

先别交。这个需求不满足 INVEST 中的“可测试”。先和产品经理把“专业”具体化：哪些场景、什么样的回答算专业（例如引用资料来源、不用口语、给出步骤）。整理成一个评测集（若干典型问题及合格标准），再把“修改系统提示词”作为任务交给 Codex，完成标准是“评测集上的合格率从 X 提高到 Y，其他类别不下降”，最后用实验开关小范围上线。
</details>

<details>
<summary>练习 5：一个用户报告“设置页保存后不生效”，但工单是两个月前的，期间做过多次发布。怎么写任务？</summary>

用出口条款：“先在当前代码中确认这个问题是否仍然存在，给出重现步骤或失败的测试作为证据。如果已经不存在，不要修改代码，说明你如何确认的，这算完成。如果存在，先写一个失败的测试，再修复。”依据是 FixedBench：代理有行动偏差，只有明确“不修改也算成功”才能显著减少多余修改。
</details>

<details>
<summary>练习 6：技术同事建议“我们直接让 Codex 自动合并通过 CI 的 PR，这样更快”。你怎么评估？</summary>

风险很大。ImpossibleBench 和 METR 的研究显示，代理会为通过检查而修改测试或钻漏洞，CI 通过不能单独证明正确；自动合并还意味着没有人了解这些代码，造成知识流失；DORA 2025 观察到 AI 采用与不稳定性上升相关。可以考虑的折中：只对极低风险的改动类型（如依赖的补丁版本更新、文档修改）在严格的 CI 和测试目录锁定下自动合并，其余仍需人审。
</details>

<a id="section-7"></a>
## 七、接下来怎么继续学

1. **动手**：拿你当前项目的一个真实任务，用第 05 章模板写任务说明，用第 06 章流程审查，记录发现的问题。
2. **建立基本功**：跟着《Pro Git》中文版第 2、3 章，在一个练习仓库里亲手做一遍提交、分支、合并、revert。
3. **定规则**：用第 08 章和第 11 章的范本，和技术同事一起定出团队的协作规则和 AI 使用规则，两周后回顾修改。
4. **继续读论文**：从本专题的 [AGENTS.md 评测](./P2_精读_AGENTS评测.md) 和 [FixedBench](./P3_精读_FixedBench.md) 进入，沿公开来源核对实验条件与失败案例。
