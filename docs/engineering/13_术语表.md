<a id="section-1"></a>
## 代码与版本控制

| 中文 | 英文 | 白话解释 | 章节 |
|---|---|---|---|
| 仓库 | repository, repo | 项目文件夹加上它的全部修改历史 | 01 |
| 提交 | commit | 一次打包存档的修改，带说明、作者和时间 | 01 |
| 差异 | diff | 两个版本之间的逐行对比，`-` 删除，`+` 新增 | 01 |
| 差异统计 | diffstat | 每个文件改了多少行的汇总 | 01 |
| 分支 | branch | 从主线复制出的独立修改线 | 01 |
| 主线 / 主干 | main, trunk, mainline | 团队共同的、应始终可运行的那条分支 | 01、08 |
| 合并 | merge | 把分支的改动并入主线 | 01 |
| 冲突 | merge conflict | 两边改了同一处，需要人决定保留哪个 | 01 |
| 推送 / 拉取 | push / pull | 上传本地提交 / 下载别人的提交 | 01 |
| 合并请求 | pull request (PR), merge request (MR) | 合并前的“申请单”，包含 diff、说明、讨论和检查结果 | 01、08 |
| 反向提交 | revert | 新增一个提交来撤销某个旧提交，不改历史 | 01 |
| 工作树 | worktree | 同一仓库的多个分支同时检出到不同文件夹 | 08 |
| 依赖 | dependency | 项目使用的第三方代码包 | 01 |
| 锁文件 | lock file | 记录每个依赖精确版本的文件 | 01 |
| 环境变量 | environment variable | 放在代码之外的配置，如 API 地址、密钥 | 01 |
| 密钥 | secret | API key、密码、令牌，绝不能提交进仓库 | 01 |
| 语义化版本 | Semantic Versioning, SemVer | 版本号写成“主.次.修订”，分别表示不兼容改动、新功能、修复 | 07 |

<a id="section-2"></a>
## 测试与质量

| 中文 | 英文 | 白话解释 | 章节 |
|---|---|---|---|
| 断言 | assertion | 测试中“结果必须是什么”的判断 | 02 |
| 单元测试 | unit test | 单独测一个小功能，快而准 | 02 |
| 集成测试 | integration test | 测几个模块连在一起能否配合 | 02 |
| 端到端测试 | end-to-end (E2E) test | 模拟用户走完整流程 | 02 |
| 测试金字塔 | test pyramid | 单元测试多、集成测试中、端到端测试少 | 02 |
| 替身 | mock / stub / fake / test double | 假装成真实依赖的假对象 | 02 |
| 变化探测器测试 | change-detector test | 只检查内部写法、不检查行为的测试，负价值 | 02 |
| 脆弱测试 | brittle test | 写死过多细节，无关改动也会失败 | 02 |
| 不稳定测试 | flaky test | 有时过有时不过的测试 | 02 |
| 覆盖率 | code coverage | 测试执行到的代码比例，不代表测得好 | 02 |
| 测试驱动开发 | test-driven development (TDD) | 先写失败的测试，再写代码让它通过，再整理 | 02 |
| 代码风格检查 | lint, linter | 自动检查写法是否规范 | 01 |
| 构建 | build | 把代码打包成可运行的程序 | 01 |
| 评测 | eval, evaluation | AI 应用的“测试”：一组代表性输入加评分方法，衡量有多好 | 10 |

<a id="section-3"></a>
## AI 编程代理

| 中文 | 英文 | 白话解释 | 章节 |
|---|---|---|---|
| 编程代理 | coding agent | 能自己读写文件、执行命令完成编程任务的 AI 程序 | 03 |
| 代理循环 | agent loop | 思考 → 行动 → 观察 → 再思考，直到它认为完成 | 03 |
| 上下文 / 上下文窗口 | context / context window | 模型做决定时能看到的全部材料及其上限 | 03 |
| 代理说明文件 | AGENTS.md（Claude Code 用 CLAUDE.md） | 写给 AI 的项目约定，每次任务前自动读入 | 03 |
| 沙箱 | sandbox | 限制代理能接触的文件和网络范围 | 03 |
| 审批策略 | approval policy | 代理什么时候必须停下来请你批准 | 03 |
| 计划模式 | plan mode | 先收集信息、提问、出计划，确认后再动手 | 03、05 |
| 子代理 | subagent | 处理有边界子任务的独立代理，有自己的上下文 | 03 |
| 基准测试 | benchmark | 一套固定考题加自动评分规则 | 04 |
| 行动偏差 | action bias | 不该动手时也倾向于动手修改 | 04 |
| 奖励投机 | reward hacking | 钻评分机制的漏洞拿高分，而不是真正完成任务 | 04 |
| 规格驱动开发 | spec-driven development | 先写规格、计划、任务清单，再让 AI 实现 | 11 |
| 氛围编程 | vibe coding | 完全靠对话驱动、不关心代码如何工作的开发方式 | 11 |

<a id="section-4"></a>
## 流程与协作

| 中文 | 英文 | 白话解释 | 章节 |
|---|---|---|---|
| 需求文档 | PRD (product requirements document) | 说清为谁、解决什么问题、怎样算成功 | 07 |
| 设计文档 | design doc | 动手前说明方案和取舍，供别人提意见 | 07 |
| 架构决策记录 | ADR (architecture decision record) | 一页纸记录一个重要技术决定的背景、决定和后果 | 07 |
| 工单 | issue, ticket | 一个具体任务的记录：描述、验收标准、负责人、状态 | 07 |
| 预发布环境 | staging | 尽量和生产一样的“彩排”环境 | 07 |
| 生产环境 | production | 真实用户在用的环境 | 07 |
| 主干开发 | trunk-based development | 小批次、每天至少合并一次、分支只活几小时 | 08 |
| 代码审查 | code review | 改动合并前由他人检查 | 08 |
| 代码所有者 | CODEOWNERS | 指定某些目录的改动必须由特定的人批准 | 08 |
| 分支保护 | branch protection | 平台强制的合并规则，如必须通过 CI、必须有人批准 | 08 |
| 持续集成 | continuous integration (CI) | 至少每天合并，每次推送自动构建和测试 | 08 |
| 持续交付 / 持续部署 | continuous delivery / deployment (CD) | 随时可一键发布 / 自动发布 | 10 |
| 敏捷 | Agile | 重视可工作的软件、协作和响应变化的价值观 | 09 |
| 冲刺 | sprint | Scrum 中固定长度（不超过一个月）的迭代 | 09 |
| 完成的定义 | Definition of Done (DoD) | 团队统一的、适用于所有工作项的“做完”标准 | 09 |
| 验收标准 | acceptance criteria | 某个需求特有的、可检验的成功条件 | 05、09 |
| 用户故事 | user story | “作为……我想要……以便……”格式的需求 | 09 |
| 在制品限制 | WIP limit | 限制同时进行的工作数量 | 09 |
| 功能开关 | feature toggle / flag | 已部署的功能用开关控制是否启用 | 10 |
| DORA 指标 | DORA metrics | 衡量交付速度和稳定性的五个指标 | 10 |
| 变更失败率 | change fail rate | 部署后需要立即干预的比例 | 10 |
| 技术债 | technical debt | 为了快而选择的、以后要付“利息”的做法 | 10 |
| 回滚 | rollback | 退回到上一个正常版本 | 10 |
| 无责复盘 | blameless postmortem | 事故后改进系统和流程，而不追究个人 | 10 |
