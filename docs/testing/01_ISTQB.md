一次测试有价值，首先因为它检查了一条明确的规则，并能区分某种正确行为与错误行为。输入数量多、执行次数多，都不能代替这个理由。本章沿着“从哪里得到规则—怎样挑输入—如何说明测到了什么”这条线，读懂等价类、边界、决策表、状态和代码覆盖之间的关系。

主读材料是国际软件测试资格认证委员会的 *Certified Tester Foundation Level Syllabus*，v4.0.1，2024-09-15，78页。它是一份认证教学大纲，用来界定基本概念和教学内容，不是比较各种方法检测效果的单篇实验论文。大纲第74页还特意说明，许多例子由教学者补充。因此本章保留其原有辨别性例子，同时把补充的订单案例明确标为自拟。[官方材料入口](https://istqb.org/certifications/certified-tester-foundation-level-ctfl-v4-0/)；[原文与教学范围说明](https://istqb.org/?download_id=3345&sdm_process_download=1#page=74)。本文件的PDF页与印刷页相同。

## 1. 先确定答案从哪里来，再决定如何选例

假设输入300元，程序显示应付280元。这个结果看起来合理，却不能仅凭“像是打了折”认定正确。需要先知道谁有资格优惠、从多少钱开始、能否叠加、非法输入会发生什么。需求、接口约定、用户故事等用来确定预期行为的材料，合称测试依据。

依据业务规定来挑输入，是基于外部规定行为的测试，也就是黑盒测试。依据内部实现来选输入，例如专门让代码中的两条路线都运行，则是白盒测试。它们区分的是**选择测试的依据**，并非谁操作、是否自动化或能不能看到源码。开发者可以先按需求设计黑盒用例，再测这些用例触及哪些代码；从接口执行的测试，也可能由内部结构指导。[原文§4.1，第39页](https://istqb.org/?download_id=3345&sdm_process_download=1#page=39)

这个区别也解释了各自的长处。如果实现改了，规定行为没变，原来的黑盒用例仍有用。白盒则随设计和实现而变，但能提示需求文档没有显露的处理路线。若某条需求根本没有实现，代码里就可能连相应的覆盖项目都没有；单看白盒覆盖很容易漏掉这种遗漏。

大纲把写测试拆成几个相连动作。先分析依据，识别需要检查的特性和条件，并按风险排序，这回答“测什么”；然后将条件细化为输入、预期结果和环境要求，这回答“怎样测”。接着准备数据、步骤和脚本，才进入执行，比较实际与预期并记录异常。这些活动可以反复交替，不必机械走成一次流水线。[原文§1.4.1，第18—19页](https://istqb.org/?download_id=3345&sdm_process_download=1#page=18)

所以，“输入200元”只是数据片段。一条可执行检查还要写清前置条件、操作、预期结果和观察方法。测试结束后，也要能追溯这条用例对应哪条规则、得到了什么结果、还有什么风险未处理；这就是大纲第20—21页强调的可追溯关系。[原文§1.4.3—1.4.4](https://istqb.org/?download_id=3345&sdm_process_download=1#page=20)

## 2. 用明确的教学规则建立一个可检查对象

下面是自拟订单案例。金额以整数“分”为单位，合法范围0至100000分。金额至少20000分，而且“会员”“有有效券”至少满足一个，就减2000分；会员且有券也只减一次。非法金额或资格类型应被拒绝，不创建订单、不扣款、不消耗券。

用a表示金额、m表示会员、c表示有效券，合法输入的规则可写成：

`有优惠 = (a ≥ 20000) 且 (m 或 c)`

`应付金额 = 有优惠时 a−2000，否则 a`

例如a=30000、m为真、c为假，应付28000分；取消会员资格后，若仍无券，应付30000分。这里的答案由规则推出，不是先运行实现再把输出登记为正确答案。

“拒绝时没有副作用”也属于规则。只见到页面报错，后台却生成了订单，仍是失败。不过，纯金额计算函数不能独自证明后台没有创建订单；不同测试对象负责观察不同范围。单元、集成、系统、验收描述的是测试对象和目的所在的层次，不应与黑盒、白盒混成一个分类。[原文§2.2，第28—30页](https://istqb.org/?download_id=3345&sdm_process_download=1#page=28)

<a id="section-3"></a>
## 3. 为什么可以从一类输入里先选一个

合法金额有十万多个整数值，逐个检查通常不合算。我们先寻找“预期按同一种规则处理”的输入集合，再选代表值，这种方法叫等价类划分。大纲的依据是：如果同一类的值确实按相同方式处理，那么某个代表暴露的错误，通常也会由同类其他值暴露。[原文§4.2.1，第39—40页](https://istqb.org/?download_id=3345&sdm_process_download=1#page=39)

先固定会员为真、无券，金额可分成负整数、0至19999、20000至100000、超过100000四类，分别预期拒绝、原价、减2000、拒绝。可选−1、10000、30000、100001作代表。字符串、空值、小数则需要根据输入约定另行识别：把它们永远合并为一个“非法类”，可能掩盖解析、类型和范围检查的不同失效方式。

这里的“等价”是测试者提出的模型，不能误读为已经证明实现对类内所有值都正确。若程序只在32768分附近溢出，选30000就可能漏掉。新的缺陷信息说明原分区对该风险太粗，需要细分或补充针对性值。分区必须非空且不重叠，也不仅用于输入：输出、配置、时间值等都能按预期处理方式分类。

要报告覆盖，先指定覆盖项目。这里的项目就是已识别的分区：

`等价类覆盖率 = 已被执行用例覆盖的分区数 ÷ 已识别分区总数 × 100%`

若模型只有上述四个金额分区，执行前三类就是3/4=75%；加入第四类才到100%。若还识别了其他无效类型，分母就不能仍写4。100%说的是当前模型中的分区全出现，不证明模型已经穷尽所有风险。

多个字段会引出下一层问题。两个字段各有0、1两类，只执行(0,0)和(1,1)，每个字段各类都出现了。大纲把这种逐字段覆盖叫Each Choice，但它没有要求(0,1)、(1,0)出现。因此“每个字段都测过”并不意味着字段之间的搭配已经测过。下一章会把这个缺口正式写成组合覆盖问题。

<a id="section-4"></a>
## 4. 边界测试为什么要关心两侧的邻居

分区之间的切换处经常对应“大于”“至少”“不超过”等判断。开发者可能漏掉等号，或把边界写错。专门选择这些切换点及邻近值的方法，就是边界值分析。它要求分区有序，而且同一分区两值之间的值也属于该分区；浏览器品牌这样的无序类别不适合硬套数值边界。[原文§4.2.2，第40页](https://istqb.org/?download_id=3345&sdm_process_download=1#page=40)

本订单在门槛附近可选19999、20000、20001分，固定会员为真，正确应付分别19999、18000、18001。如果把`a≥20000`误写为`a>20000`，只有中间那次会暴露差别。检查10000与30000都正确，不能区分这两种实现。

大纲区分两值和三值边界分析。对每个边界值，两值版本要求它本身及相邻分区最近的值；三值版本还包括另一侧邻居。原文给出的例子说明为何多一个值可能有意义：需求为`x≤10`，实现却写成`x=10`。

| 输入 | 需求结果 | 错误实现结果 |
|---|---|---|
| 10 | 真 | 真 |
| 11 | 假 | 假 |
| 9 | 真 | 假 |

只测10、11，错误实现可以通过；加入9才把它区分出来。这不是“测试越多越好”的口号，而是新增值针对一种明确漏检机制。

计算覆盖率时，分母应是所选边界方法规定的完整项目集合。每个边界都要考虑，重复值只算一次，还要先说明数值类型及最小步长。上面的三个值只是原文局部辨别例；若模型把相邻区间的11也识别为边界，三值项目还需考虑它另一侧的12。不能把任意三个“边界附近值”称作整个输入模型100%三值覆盖。

<a id="section-5"></a>
## 5. 当多个条件一起决定结果，怎样发现遗漏规则

金额、会员、券的组合决定动作。与其凭记忆列几个场景，可以把条件组合和对应动作完整排出来，这叫决策表测试。大纲中每列是一条规则，行列出条件与动作；下表为便于阅读转置成一行一条规则，思想相同。[原文§4.2.3，第41页](https://istqb.org/?download_id=3345&sdm_process_download=1#page=41)

| 金额达标 | 会员 | 有效券 | 动作 |
|---|---|---|---|
| 否 | — | — | 原价 |
| 是 | 是 | — | 减2000分 |
| 是 | 否 | 是 | 减2000分 |
| 是 | 否 | 否 | 原价 |

“—”表示在该规则中不影响动作，不能理解为不可能出现。第一行无论会员、券怎样，金额不足都不优惠；第二行会员已足够满足资格，因此券不影响动作。若三个条件彼此独立，未合并的布尔表有2³=8种组合，上表通过合并相同动作减少规则数。

合并表有四条可行规则，执行三条覆盖率就是3/4；原始八条表则使用另一分母。报告必须说明以哪张表为准。完整决策表还可删去由真实约束排除的组合，但“罕见”与“不可能”不同；为了表格好看删掉罕见规则，会制造虚高覆盖。

合并也不能取消具体风险。会员且有券虽然被第二行包含，但“只减一次”正是可能写错的地方，值得另选两项都真的输入，检查实现有没有扣两次。这条测试的理由来自特定失效方式，而非形式上多占一条。

大纲还区分只用真假值的表和允许区间、多值类别的扩展表。它们共同的好处不只是选测试：在给每个组合写动作时，可能发现需求没有答案，或两条规定给出矛盾答案。此时应先澄清需求，不能替业务随意填一格后继续验收。

<a id="section-6"></a>
## 6. 当前输入一样，过去不同，结果也会不同

同一条支付成功回调，第一次可能改变订单状态，第二次却不应重复记账。只列金额和资格已经不够，还要建模状态及事件。把“处在哪个状态，收到什么事件，在什么条件下执行什么动作”写清，再据此选事件序列，就是状态转换测试。[原文§4.2.4，第41—42页](https://istqb.org/?download_id=3345&sdm_process_download=1#page=41)

继续用自拟规则：待支付可以支付或取消；已支付收到同一回调，维持已支付且不再记账；已取消收到支付回调，应拒绝入账并转异常处理。以下小表中的“无效”指该事件不允许正常改变订单，仍须检查规定的拒绝反应。

| 当前状态 | 支付回调 | 取消请求 |
|---|---|---|
| 待支付 | 转已支付，记账一次 | 转已取消 |
| 已支付 | 留在已支付，不再记账 | 无效，拒绝 |
| 已取消 | 无效，转异常处理 | 留在已取消，不重复操作 |

检查“创建→支付”与“创建→取消”，三个状态都出现了，但没检查重复回调和已支付后取消。大纲因此区分三个目标：所有状态覆盖统计到过多少状态；有效转换覆盖统计走过多少合法边；所有转换覆盖还包括尝试无效转换。它们的分母分别是状态数、有效边数、状态表中有效与无效转换总数。

在这个明确模型下，三状态全出现可达100%状态覆盖，却仍远未完成六格检查。有效转换覆盖也叫0-switch，表示检查单次转换，并不要求所有两步、三步或更长顺序。为了减少一个无效事件提前结束流程、遮住后一个错误，大纲建议一条用例中只尝试一个无效转换。一次拒绝并不能证明同一长序列中每个非法动作都已被检查。

<a id="section-7"></a>
## 7. 回到实现：运行过的结构告诉了我们什么

黑盒用例完成后，还可以看它们实际运行过哪些实现。这产生两种基础度量。语句覆盖的分母是可执行语句，分子是实际执行过的语句；源码一行可能含多个语句，注释也不是可执行语句。分支覆盖则统计控制流图中节点之间的控制转移，包括有条件和无条件转移，不能普遍简化成“if数量乘二”。[原文§4.3，第42—43页](https://istqb.org/?download_id=3345&sdm_process_download=1#page=42)

例如先设`pay=amount`，符合优惠条件就执行`pay=amount−2000`，最后返回pay。只测一个享受优惠的订单，所有这些语句都可以运行，但没走过“不优惠”的路线。同一对象、同一控制流口径下，100%分支覆盖包含100%语句覆盖，反过来不成立。

更关键的是，执行过不等于验证正确。某除法只有分母为零才失败，执行该语句一次而分母非零，问题仍会漏掉；全部分支都走过，也可能没走到特定分支组合形成的路径。与此同时，覆盖只能数已经存在的实现项目，无法自动指出完全遗漏的需求。这正是结构信息和需求预期应结合使用的原因。

大纲没有要求所有测试都从这些形式模型产生。探索式测试让测试者边学习系统、边设计和执行新检查，可用时间盒与测试章程明确目标；基于经验的错误猜测能补上模型未想到的失效方式。实现前由业务、开发、测试共同澄清验收条件，并先写测试的协作办法，则帮助减少需求歧义。它们分别补充发现和预防问题，不能用“只是经验”一笔抹去。[原文§4.4—4.5，第44—46页](https://istqb.org/?download_id=3345&sdm_process_download=1#page=44)

最终是否结束测试，还要结合风险、未修缺陷、失败用例和项目目标。覆盖率提供一个有定义的观察角度；它不独自承担“软件已经足够好”的决定。[原文§5.1.3与§5.2.3，第49、53页](https://istqb.org/?download_id=3345&sdm_process_download=1#page=49)

<a id="section-8"></a>
## 8. 自测：把方法用回选例理由

**题一：两个字段各有两个等价类，(0,0)、(1,1)全部通过，能否说所有字段组合已验证？**

不能。它满足逐字段各类出现的Each Choice，但缺(0,1)、(1,0)。要说清“类覆盖”与“组合覆盖”分别统计什么，不能共用一个100%。

**题二：需求x≤10，执行10和11均正确，为什么9有新增价值？**

错误实现x=10也能通过10和11；9使正确结果为真、错误结果为假，因此可以区分这两个实现。这是原文的辨别性例子，不是随意追加一个输入。

**题三：已支付后重复回调维持原状态，是否可从状态表删去？**

不能。它虽不改变状态，却可能承担“不重复记账”的关键要求，是有动作约束的有效自循环。只看状态不变，仍需检查有没有重复副作用。

**题四：全部实现分支运行过，为什么还要检查需求清单？**

因为未实现的需求可能没有任何分支可供计数；错误计算值也可能完全不改变覆盖结果。结构覆盖帮助找测试触及实现的缺口，需求清单与预期结果负责检查应该实现的行为。

本章的阅读结论是：先明确规则，再把规则中的分类、边界、组合与历史状态变成可解释的覆盖项目，最后让具体用例提供执行与判错证据。本章完成的是大纲定义的重构和教学演算，没有把订单例当真实项目实验，也没有由大纲推出各种技术统一的优劣排名。
