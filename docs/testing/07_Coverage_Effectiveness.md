## 一、问题并不是“执行过的代码有没有用”

代码没有被运行，测试通常就没有机会发现其中的问题；但运行过以后，还需要输入触发错误、错误传播出来，并被测试判定为失败。因此，覆盖率回答“测试走到了哪里”，检错能力回答“测试发现了多少错误”，二者不能直接画等号。

论文针对一个更具体的问题：如果两个测试集包含的测试方法一样多，覆盖率较高的那个，是否更善于检错？这一步控制很关键，因为加入更多测试，既可能扩大覆盖范围，也可能多发现错误。若把不同大小的测试集混在一起，二者的共同增长容易被误读为覆盖率本身提供了很强的质量信息。（[PDF 第 1 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=1)）

作者的贡献是实证证据和测量比较，并非提出新测试算法。按本文对前人的梳理，Gligoric 等已经研究过未达到完整覆盖要求的测试集，并发现大项目中测试数量与检错效果高度相关；本研究进一步按数量分组，同时扩大项目规模。这里的历史关系仅依据本文转述，没有独立核验被引研究。（[PDF 第 2–3 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=2)）

<a id="section-2"></a>
## 二、为什么从现有测试中抽样，并固定测试数量

研究选择 Apache POI、Closure、HSQLDB、JFreeChart、Joda Time 五个 Java 开源项目，横跨文档、编译器、数据库、图表和日期处理。表 2 的 Java SLOC 为 80,462–724,089；这里是作者用 SLOCCount 测得的源码行数，不能直接等同于后文语句覆盖率中的可执行语句数。项目需有较多开发者编写的测试，并采用 Ant、JUnit，以便统一收集数据。这是按条件选样，不能代表所有软件。（[PDF 第 3–4 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=3)）

每个项目已有的完整测试集合称为 master suite。作者从中随机、不放回地抽取测试方法：每个集合内部不会重复抽同一方法，但不同集合可以共享方法。规模依次取 3、10、30、100、300、1000、3000，只保留小于该项目完整测试数量的档位；每档生成 1000 个集合，并保留 JUnit 的准备与清理步骤。根据表 2 重算，五项目分别有 6、7、5、6、7 档，合计 31×1000＝31,000 个测试集。（[PDF 第 4 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=4)）

这样的设计允许先混合不同规模看总体关系，再在“同一个项目、相同方法数”内比较，减少程序差异和测试数量的干扰。它还避免只研究达到 100% 覆盖的少见测试集。不过，31,000 是反复抽样的集合数，底层仍只有五个项目；方法数相同也不等于断言数、执行时间或开发成本相同。因此，研究回答的是数量控制后的关联，不能直接回答“投入相同工时，追求覆盖率是否更划算”。

<a id="section-3"></a>
## 三、关键在于检错指标的分母

作者用 PIT 对程序作小修改，例如改变常量或条件，得到“变异程序”。测试在修改后失败，就称为杀死这个变异程序。它提供大量可控的错误对象，但仍只是实际缺陷的替代测量。（[PDF 第 3–4 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=3)）

有些修改不会改变可观察行为。图 1 中计数器逐次加一，到 10 时退出；把 `== 10` 改成 `>= 10`，退出行为不变。这叫等价变异，测试不可能把它当错误检出。逐个判断成本很高，因此作者采用近似：完整测试集杀不死的变异程序，都按等价变异排除。这并不等于证明它们真的等价。

下面将第 5 页文字定义写成公式。对同一项目，令 M 为排除后保留的变异程序数，C 为某测试集执行到其修改位置的数量，K 为实际杀死的数量，则 K≤C≤M：

- 原始检错分数 R＝K/M：在全部保留对象中发现了多少。
- 归一化检错分数 N＝K/C：在有机会发现的对象中发现了多少，要求 C＞0。

由定义可得 R＝(C/M)×N。这是读者补出的恒等式：总检出比例同时取决于触及范围与范围内的检出比例。C/M 是保留变异体中，其修改位置被执行到的比例，仍按变异体计数；它不能直接替换成去重后的位置覆盖率或语句覆盖率。原文没有交代 C＝0 的具体处理，因此不能替作者补上规则。

归一化改变了问题：新测试若执行了很多新位置，却几乎不检出错误，R 可能上升，N 却下降。它帮助区分“走得更广”和“检查得更深”，两者服务不同评价目的。尤其要注意，完整测试集的两个分数必然为 1，是筛选分母造成的，并不证明它能发现全部真实错误。以 POI 为例，27,565 个变异中排除 9,630 个，重算比例为 34.94%，即表 2 四舍五入后的 35%；最终 M 只有 17,935。（[PDF 第 4–5 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=4)）

覆盖率由 CodeCover 测量，包括执行语句比例、决策分支比例，以及文中称为 modified condition coverage 的 MCC。原文描述 MCC 达到完整覆盖时，每个含 n 个条件的决策需要 2ⁿ 个测试案例。作者将其与 MC/DC 联系起来，但两者不能视为本研究直接测过的同一个指标；本文也没有测数据流覆盖率。（[PDF 第 4–5 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=4)）

<a id="section-4"></a>
## 四、证据怎样支撑标题，又怎样限制标题

第一步看测试数量。图 2 横轴为测试方法数，采用对数刻度；纵轴是 N；每个箱体代表一个项目某一规模的 1000 个测试集。多数项目随规模扩大而提高，HSQLDB 则先略降、随后回升。作者报告拟合的调整后 R² 为 0.26–0.97，说明项目差异很大，不能概括成“多加测试必然提高检查深度”。模型同时使用数量及其对数，也不宜把该 R² 直接解释成原始数量与效果的简单线性相关。（[PDF 第 5–6 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=5)）

第二步忽略数量，考察覆盖率与检错分数。作者使用 Kendall τ：它比较测试集的排序是否一致，不要求二者呈直线关系。表 4 中覆盖率与 R 的 τ 为 0.79–0.95，看起来很强。但换成 N，HSQLDB 的三个 τ 都是 −0.35；覆盖更多时，总共杀死的变异更多，却未必把新增覆盖区域检查得更彻底。这不是两张表互相矛盾，而是分母改变了评价对象。（[PDF 第 5–6 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=5)）

第三步才是核心：在同项目、同规模内重新计算。图 3 每列一个项目、每行一个规模，横轴覆盖率、纵轴 N；底行混合规模后的趋势，不能替代各规模内部的点云关系；多数项目上升，HSQLDB 则保留负相关例外。作者报告，控制数量总会降低相关性，通常 N 对覆盖率相关较低，R 对覆盖率相关中等。Joda Time 从忽略数量时约 0.80–0.85 降至接近零；Closure 在 N 上也出现类似变化。反例是 POI：R 的相关性从 0.94 降至 0.46–0.85，部分分组仍然较强。因此，证据支持“覆盖率不能普遍可靠地代表检错能力”，不支持“任何项目中覆盖率都无价值”。完整分组系数不在 PDF 内，无法逐项复算。（[PDF 第 7 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=7)）

最后，三种覆盖指标给出的关系相近。表 5 将所有项目、所有测试集汇总，指标间 τ 为 0.91–0.92，Pearson 相关为 0.97–0.99；图 3 中同组的三色点云形状也相近。这支持本样本中更复杂指标没有明显增加排序信息。图 4 只是作者的假想示意，说明换横轴本来有可能改善关联，并非新增实验数据。上述结果也没有直接比较“按不同覆盖标准重新编写测试”的效果或成本。（[PDF 第 8 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=8)）

<a id="section-5"></a>
## 五、结论最依赖哪些假设

最重要的假设是：保留下来的变异程序，足以代表研究想谈的检错能力。作者承认，排除对象未必是随机子集：若开发者特别善于测试边界错误，这类变异更容易被保留，完整测试集共同漏掉的困难错误则会被排除。于是研究可能更充分反映已有测试擅长的错误。另一方面，作者引用前人支持变异测试与真实缺陷的联系；本次只读原文，无法独立确认这些支持有多强。（[PDF 第 9 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=9)）

其次，固定方法数仍是相关分析，不是随机分配“提升覆盖率”干预。归一化也只描述已触及位置的表现，没有让不同测试集面对完全相同的错误难度。作者称表 3–4 的各相关系数在“99.9% 水平”上显著，但显著不等于关联强或具有因果性；这是对原文报告的转述，不是把相关系数解释为结论正确的概率。作者还检查了排序并列问题，最差计算中并列比较占 4.6%；没有原始数据，本讲义不能复核显著性或构造置信区间。（[PDF 第 5–6、9 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=5)）

最后，生成集合很少达到极高覆盖率，因此不能排除高覆盖区间存在不同关系。五个开源 Java 项目、特定工具和已有测试库，也限制外推。尤其是对航空 MC/DC 要求的讨论，比实际测量对象走得更远，不能据此断言该要求无效。（[PDF 第 9–10 页](https://www.cs.ubc.ca/~rtholmes/papers/icse_2014_inozemtseva.pdf#page=9)）

<a id="section-6"></a>
## 六、值得组会继续讨论的问题

**相同方法数、相近覆盖率时，补强断言能否比增加覆盖范围更稳定地提升真实缺陷检出率？** 这是从本文“触及位置不等于检出错误”推导出的研究提议，不是论文已验证的结论。

可以在同一项目、同一基线测试上比较两种等预算修改：一组加强已覆盖行为的判断，另一组拓展覆盖范围；用独立的真实缺陷集合评价，同时记录工时和方法数。若前者覆盖率几乎不变却检出更多缺陷，说明原指标遗漏了重要质量维度；若后者持续更好，则表明本文的抽样关联不足以替代改进策略实验。难点是预算如何公平对齐，以及获得不偏向原测试集的真实缺陷。当前证据最稳妥的用途，是用覆盖率定位未测试区域，同时避免把单一覆盖率门槛当成测试质量的充分证明。

## 七、用一个小例子检查你是否理解分母

下面是教学构造，数值不是论文实验结果。设保留变异 M＝100，测试集 A 触及 C＝40 个并杀死 K＝30 个，测试集 B 触及 80 个并杀死 40 个。A 的 R＝30%，N＝75%；B 的 R＝40%，N＝50%。B 总共检出更多，A 在所触及范围内的检出比例更高。只报告其中一个数，会遗漏另一个质量维度。

再问：A 是否一定有更好的断言？不能。A、B 可能碰到不同难度的变异，N 只是所达位置上的表现，并没有自动控制错误难度。需要在相同触及对象上比较，或对独立错误集合做等预算实验，才能更接近这个问题。

**自测一：完整测试集取得 R＝N＝100%，为什么不是“完美测试”的证据？**

参考答案：本研究用完整测试集能杀死的变异定义保留集合 M，其他变异被排除；完整集满分是这个选择规则造成的。它共同漏掉的真实错误不在分母内。

**自测二：控制方法数后关联变弱，是否说明增加覆盖率没有因果作用？**

参考答案：不能。研究比较从已有测试库抽样得到的集合，测量的是关联；它没有随机安排两组团队分别扩展覆盖或增强断言，也没有控制实际编写成本。

**自测三：这篇论文能否直接推翻航空 MC/DC 的使用要求？**

参考答案：不能。实际测量的项目、覆盖指标、错误代理和工作环境都不等同于航空软件的评审情境；尤其不能把文中 MCC 与 NASA 指南的 MC/DC 混为一谈。

**这一章与前后文的连接**：Zhu 讨论覆盖标准在形式上要求什么，本文研究这些测量在有限样本中怎样关联检错能力，Oracle 综述再解释为何“走到错误”以后仍需要可靠的判断。三者并不相互否定，它们在证据链中回答不同层次的问题。
